# 批次 61 · 全城连续正交方格路网 · 方案设计

> 日期：2026-10-20 ｜ 分支：`main`（§10.1）
> 承接：批次 59「邻接次干道正交化」。本批把批次 59 的**局部正交化**升级为**全城方格网**。
> 起因（用户反馈 2026-10-20）：「**街道还是很乱，没有连续上，道路应该是连续的，一块块还是斜向的**」。

---

## 1. 问题诊断：为什么批次 59 之后街道仍然「乱、不连续、斜向」

批次 59 只做了**局部**处理：把「每区连 2 最近邻」的斜向 connector 拆成曼哈顿 L 形两腿。
它没有触及三个更根本的问题：

| # | 症状 | 根因（已逐条代码核实） |
|---|---|---|
| ① | **一块块还是斜向的** | 32 个城区的**中心坐标本身是散点**（`ClientWeb/src/types/virtualCity.ts::VIRTUAL_CITY_DISTRICTS` / `ServerGo/game/virtual_city/districts.go::DistrictDefs`）。x 坐标集合为 `-46,-44,-40,-32,-24,-22,-20,-14,-12,-10,-8,0,2,8,10,14,22,24,36,38,40,44,46`——**任意两个相邻值之差都 < 9**，而街区半宽 4.0 + 路廊半宽 0.7 = 4.7 ⇒ **全城不存在任何一条能连续贯穿、又不切进任何街区的南北向街道线**（可容许的轴线只有 `x=16` 与 `x=30` 两条）。街区与街道无法构成正交关系 ⇒ 视觉上永远是「一堆斜着的块」。 |
| ② | **道路不连续（碎成一段段）** | 路网由 3 类**互不相接**的线段拼成：① 36 条 connector（L 形，拐角坐标由 `connectorLegs` 逐对独立评分决定，**两条 connector 之间毫无共线关系**）；② 4 条 arterial（`x=±18 / z=±26`）；③ 17 条 edgeLink（径向）。三类线段端点**基本不对齐**，每条 connector 又是 2 段独立 mesh ⇒ 路口处出现**缺口与错位**，看上去就是「一块块」。 |
| ③ | **斜向路** | `edgeLink`（批次 59 §2.4 显式保留的「绕城高速联络线」）是**从区心沿径向直插高速环**的直线 ⇒ 17 条斜向干道贯穿全城。批次 59 文档把它判为「真实语义」而保留，但用户反馈证明它正是「斜向」观感的主因。 |
| ④ | 环路与方格网互斥 | `FirstRingRoad`（r=20 圆环）与 `RingRoad`（CBD r=5.6 圆环）在方格网里必然切进街区：新网格下街区中心 (12,12) 到原点 16.97，加半宽 4 ⇒ 角点 r=22.6 ⇒ **半径 20 的圆环会从街区内部穿过**。 |

**结论**：局部正交化无法解决——**必须先让城区落在方格上**（街区方格化），再让街道成为方格边界（连续正交），并**删除与方格网互斥的圆环**。

---

## 2. 方案：街区方格化 + 街道连续化

### 2.1 网格定义（唯一事实来源：`ClientWeb/src/components/virtualCity/cityGrid.ts`）

- **街区单元（block cell）边长** `GRID_CELL = 12`（世界单位；1u = 10m ⇒ **120 m 街区**，与真实城市次干道围合的街坊尺度同量级）。
- **街区中心** = `(i·12, j·12)`，`i, j ∈ [-3, 3]` ⇒ **7×7 = 49 个街区单元**，城区中心取值范围 `[-36, 36]`。
- **街道中心线** = 街区边界 ⇒ `x, z ∈ {6 + 12k}`（`k ∈ [-4, 3]`）⇒ `…, -42, -30, -18, -6, 6, 18, 30, 42`。
  - 街区宽 8（建筑街墙 `EDGE_CENTER=2.85` + 楼宽/进深余量），街道中心线在 ±6 ⇒ 建筑外缘（≈3.75）到路缘（6 − 0.7 = 5.3）之间留 **1.55u = 15.5 m 的人行道/绿化带**（真实城市尺度）。
- **道路等级**：
  - **次干道（side）**：全部街道线。
  - **主干道（main）**：`x = ±18` 与 `z = ±18` 两条中环线（贯穿全城，把 49 街区分成 3×3 的大分区）。
  - **外环快速路（main）**：`x = ±42` 与 `z = ±42` 四条外沿线（构成方形城市外环）。
- **每条街道 = 1 条整直线段**（不是几十段拼接）⇒ 路面是**一张连续的长面片**，天然无接缝、无错位。

### 2.2 城区落位（32 区 → 32 个街区单元）

目标：保持各区**相对地理**（CBD 居中、港口在西、体育在南、空港在东北、山居在北），
同时让位移最小。方案：**以当前坐标为代价的最小位移注入匹配**（匈牙利算法，代价 = 位移平方），
并强制 `finance`（金融 CBD）留在 `(0, 0)`。

### 2.3 街道清单（连续正交，无一例外）

**运河与街道的关系**：`z = 18` 恰是街区行 12（占 z∈[8,16]）与街区行 24（占 z∈[20,28]）之间的
4u 空隙中线 ⇒ 运河带 `[16.5, 19.5]` **不切任何街区**。该行**不生成东西向街道**，
南北向街道在运河处**架桥通过**（8 处：x = -42,-30,-18,-6,6,18,30,42）。

**环城高速与方格网的关系**：`r = 58` 的圆环与外沿街道 `x = ±42` / `z = ±42` 共 **8 处正交交叉**
（如 x=42 与 r=58 交于 z = ±40.9）⇒ 天然形成 8 座互通，**无需任何斜向联络线**。

### 2.6 街道交叉口（信号灯 / 停止线 / 人行横道）

- 南北向街道 × 东西向街道 = 8 × 8 = **64 个正交交叉口**（`gridJunctions`）。
- 优先级：主干道 × 主干道 > 主干道 × 次干道 > 次干道 × 次干道；
  十字路口布红绿灯（四向），次干道 × 次干道布人行横道 + 让行标。
- 环城高速 × 外沿街道 = 8 处互通（立交/匝道简化表现）。

## 5. 验收标准（可判定）

1. **零斜向**：全城路网中不存在任何非轴对齐线段（`Road.tsx` 的 `angle` 恒为 0 或 ±90°）。
   环城高速是圆，不计入路网线段。
2. **零碎段**：南北向街道 8 条、东西向街道 8 条，**每条都是一条整长线段**（端点恰在 ±42 边界）。
3. **路口对齐**：任一 N-S 街道与任一 E-W 街道的交点都在**另一条的内部**（真交叉，不是贴边）。
4. **街区内无路**：所有建筑（`building_layout.buildingsFor`）的占地矩形与任何街道中心线的
   距离 ≥ 4.7（街区半宽 4 + 路廊半宽 0.7）。
5. **保留地不压路**：体育场 / 码头 / 港池 / 运河均不切断任何街道线段（运河行除外，该行不生成街道）。
6. **CDP 顶视截图**：正午顶视（phi≈0.05）下能一眼看出规则方格网，**无斜向长线**、**无断裂**。
7. `cd ClientWeb && npx tsc --noEmit` 通过；`npm run build` 通过。
8. `cd ServerGo && go build -o LsmAgentGame main.go` + `go test ./...` 通过。

## 6. 风险与兜底

| 风险 | 兜底 |
|---|---|
| 城区移动导致「城市变小」（外沿 ±46 → ±36）而显得空 | 49 个街区单元中 32 个建城、**17 个空单元填充城市功能用地**（绿地广场 / 停车场 / 变电站 / 加油站 / 施工工地 / 口袋公园），沿用既有 `props/` 资产 |
| 运河改位导致水面/桥/码头错位 | 改的是**单一常量** `CANAL_Z`，`WaterPlane` / `CanalBridge` / `Road` / `cityObstacles` 同源消费；桥位由「街道 × 运河」自动生成 |
| 环路删除后红绿灯/停止线布点失据 | 统一改用 `gridJunctions`（64 个正交交叉口） |
| 建筑密度下降（街区从散点变方格） | 方格网内 32 个街区满铺，空单元用城市功能用地填充（见上） |
