## 1. 背景与现状

CityChrome 采集 Agent（`ServerGo/citychrome/agent.go`）按 mission 配方驱动 Chrome（经 go-web-debug-tool CDP 底座），已有 7 工具（web_open/control/eval/look/list/close/done）。缺口：

1. **无规划阶段**——mission 直接进执行循环，Agent 不先提交计划，「规划-执行」轨迹不可观测；
2. **无跨 mission 经验记忆**——上次哪个源成功/失败、用了几步，本次 mission 一无所知；
3. **步数效率**——「打开+读正文」要 2 步（web_open + web_eval），批次76 macro 曾 14 步耗尽；
4. **无发现能力**——备选站全失败即 mission 失败，无检索兜底；
5. **无任务遥测可视化**——前端实时看板看不到采集任务的运行情况；
6. **页面卫生**——Agent 忘记 web_close 时页面泄漏。

数据源登记册（45 条，批次76）经 2026-10-22 逐项复测，**完整覆盖用户本次提供的 38 项站点清单**（综合财经5 / A股4 / 港股1 / 美股1 / 贵金属7 / 期货2 / 加密1 / 宏观4 / 时政军事8 / 数据接口 5 行 6 条），零缺口，登记册不再扩容。

## 2. 目标

1. **plan 规划**：新工具 `web_plan`——mission 第一步强制提交结构化规划（目标站 + ≤5 步 + 换源预案），落任务遥测；
2. **执行提效**：新工具 `web_read`——一步完成「打开页面+读正文」（原 2 步）；
3. **操作获取**：新工具 `web_search`——必应中国 SERP 只读提取，固定源全失败时检索替代公开数据页（仍禁登录/验证码/表单）；
4. **经验闭环**：mission user prompt 自动注入「最近成功（source/步数/条数）+ 最近失败原因」，Agent 据此优化规划；
5. **遥测可视化**：`MissionRecord` 环形记录（≤20），HTTP 快照新增 `missions[]`，实时看板新增「采集」子页；
6. **Agent 知晓**：`realworld_info` 新增 `keyword`（op=news 标题关键词过滤），城市居民 Agent 可按主题查新闻；
7. **页面卫生**：Toolset 跟踪 OpenedPages，mission 结束 best-effort 自动回收。

### 3.1 工具集 7→10（mcp_tools.go）

| 工具 | 输入 | 行为 | 返回 |
|---|---|---|---|
| `web_plan` | `{goal?, steps: string[1..8]}` | 本地工具（不走底座 HTTP）；steps 每条非空 ≤80 rune、goal ≤80 rune；写入 Toolset.Plan | `已记录规划 N 步: s1 → s2 …` |

| `web_search` | `{query, count?}` | 打开 `https://cn.bing.com/search?q=<esc>&ensearch=0` → BatchEval 提取 `#b_results > li.b_algo`（title/url/snippet≤120字）→ **自动关页**；count 缺省 5、钳制 1..10；query 非空 ≤100 rune；0 结果返回正文前 600 字兜底 | JSON 结果列表文本 |

### 3.2 MissionRecord（新文件 mission_log.go）

```go
type MissionRecord struct {
    ID         string `json:"id"`          // "<category>-<startedAtUnixMilli>"
    Category   string `json:"category"`
    StartedAt  int64  `json:"started_at"`  // Unix 秒
    DurationMs int64  `json:"duration_ms"`
    Status     string `json:"status"`      // running | ok | fail
    Source     string `json:"source"`      // 成功时 payload.Source
    StepsUsed  int    `json:"steps_used"`  // 实际 LLM 轮数
    MaxSteps   int    `json:"max_steps"`
    Plan       string `json:"plan"`        // goal + steps 以 " → " 连接，≤200 rune
    Quotes     int    `json:"quotes"`      // 提交 payload.quotes 条数（已过校验）
    News       int    `json:"news"`        // 提交 payload.news 条数
    Error      string `json:"error"`       // 失败原因，≤300 rune
}
```

`MissionLog`：容量 20 环形缓冲（mutex）；`Append`（同 ID 覆盖更新）/ `Snapshot`（新→旧副本）/ `LastOK(cat)` / `LastFail(cat)`。

### 3.3 Agent 循环增强（agent.go）

1. roleText 追加【规划与效率(批次77)】：第 1 步必须 `web_plan`（≤5 步、含换源预案）；简单读取优先 `web_read`；备选站全失败时 `web_search` 检索替代公开页。既有纪律段逐字保留。
2. **经验注入**（missionUserPrompt 末尾，有记录才加）：
   ```
   【上次采集记录(自动注入,据此优化本次规划)】
   最近成功: source=<Source>, 步数=<StepsUsed>, 提交 quotes=<Q> news=<N>
   最近失败原因: <Error>
   ```
3. **遥测**：Agent 持 MissionLog（`SetMissionLog` 注入）；RunMission 入口 Append(running)，成功/失败原地更新（DurationMs/Status/StepsUsed/Plan/counts/Error）。
4. **页面回收**：RunMission defer 遍历 Toolset.OpenedPages best-effort `CloseChromePage`（2000 幂等）。
5. `MaxStepsPerMission` 默认仍 14（web_read 省步 ≥ web_plan 多耗 1 步，净中性）。

### 9.5 工程教训

1. **共享工作区禁用 `git stash`** —— backend SubAgent 一次 `git stash -u` 让主 Agent 侧「改动凭空消失」（含 4 个未跟踪新文件），排查耗时远超收益；SubAgent 一切还原操作必须避开共享工作区。
2. **前端 CDP 登录态注入需双键** —— `lsm.auth`（zustand persist）**与** `lsm.token`（`hydrateFromStorage` 的第二条件）缺一即被降级为未登录（症状：所有 API 401、看板空态）。且注入须在目标页加载后执行（首页 persist 回写会覆盖注入值）。
3. **看板来源列是 Agent 输出的第一道质检口** —— `source` 字段若不限语义，实机就会被塞进解释性长串；提示词纪律 + 校验层截断双保险才稳。
