### 1.2 模板参数化引擎（`scenario_templates.go`）

```
kind   = base.Kind + "__" + axis.Suffix + "_" + value.Key   (多轴用 __ 连接)
name   = base.Spec.Name + "·" + value.Label                 (多轴用 · 连接)
profile = base.Profile × (Π value.Scale)  然后 逐字段 += Σ value.Adjust
```

- **纯函数、确定性、零 RNG**（单测断言同模板两次派生逐字段相等）。
- 单模板变体数 ≤ 256、单轴取值数 ≤ 32、轴数 ≤ 4（代码级防御）。
- `Adjust` 是**加性**调整，在缩放**之后**应用；`Scale` 缺省 0 视作 1.0。
- 全目录 `kind` **唯一性**单测钉死（1,203 个 kind 无重复）。

### 1.3 `scenarioProfile` 扩 2 个旋钮

| 新旋钮 | 映射 | 语义 |
|--------|------|------|
| `WageShockPct` | `Labor.AvgWageCNY`（按比例，带非负下限） | 劳动力价格变化 |
| `RevenueShockPct` | `Labor.RevenueCNY`（按比例，带非负下限） | 企业营收冲击 |

**零新增 World 持久化状态**；`Labor` 为 nil 时跳过。既有 12 个旋钮语义与既有 101 条
场景的幅度值**逐字不变**。

### 1.4 目录检索 API（`scenario_catalog_query.go`）

```go
func ScenarioCatalogSearch(query, group string, limit int) []ScenarioSpec
func ScenarioCatalogSearchErr(query, group string, limit int) ([]ScenarioSpec, error) // 未知组 → 35064
```

- `limit` 缺省 30、上限 200（检索层强制）。

- `ScenarioDimensionIndex()` **恒定体积**：每组只给前 3 个 `samples`。

### 1.5 指标历史环（`room_metric_history.go`）

## 4. 后端 · 其它 Agent 适配（职责线 4）

### 4.1 修死链 §2.5b（本批最重要的正确性修复）

**实证**：全仓 `grep -rn "msg.Type"` 在生产代码里**零命中** —— 批次 81 的
`send_agent_message` 正文被三个 bus handler 全部丢弃：

| handler | 收 `"message"` 的旧行为 |
|---------|------------------------|
| `City-Chrome` | `payload.(map[string]any)` 断言失败 ⇒ `category==""` ⇒ **误触发一次全类目采集** |
| `City-Human` | 无视 Type 与 Payload ⇒ 返回居民摘要 |
| `City-WebGL-Show`（房间级） | `ParseDisplayRequest` JSON 反序列化 ⇒ **类型错误** |

**本批修法**：新增 `HandleBusMessage(ctx, msg)` 作为**统一入口**，**按 `msg.Type`
分支**；载荷统一 `map[string]any{"text": ...}`（**额外接受裸字符串**，兼容批次 81
既有 `send_agent_message` 的旧载荷形态）。

| Agent | `"message"` 分支行为 |
|-------|---------------------|
| `LsmAgentGame-City-Chrome` | 确定性关键词表 → 8 个采集类目（零 RNG、零 LLM，不命中兜底 `news`）→ 经**既有** `RefreshWithGoal` 入队（复用 60s 同类目限流 + 单飞队列 + `llmSema` 节流）→ 立即回「已受理…」→ **采集完成后**经 `NotifySystem` **上行**结果摘要 |

`citychrome.NotifySystem(ctx, hub, roomID, text)` / `ReportToSystem`；

### 7.2 `game/virtual_city` 的 MC 测试 —— 判定：**非本批引入**（分三层）

本批有 5 条职责线并行跑测试，多个测试二进制同时抢 CPU（load 一度 10+）。在
**git worktree 干净 HEAD 基线**（`e728ae4f82`，零并行争抢）单独跑同一组 MC 测试：

| `TestMCAB_Boundary` | ✅ PASS 14.59s |
| `TestMCCause_*`（4 项） | ✅ PASS |

⇒ 这些测试**本来就慢（分钟级）**，在满载时才超时。本批工作区
`go test ./game/virtual_city/ -skip 'MC'` → **ok（414s）**。

**② `TestMCSmoke` 的失败是 `main` 上的存量问题 —— 已做逐位对照实证。**

同一测试（`-run '^TestMCSmoke$' -count=1`，各自单独跑、无并行争抢）在
**干净 HEAD 基线**（`e728ae4f82`，零批次 84 改动）与**本批工作区**各跑一次：

**8 项门禁值 + 失败样本数逐位相同，墙钟差 0.75 秒。** MC 是种子确定性 —— 数值
逐位相同即证明**模拟行为零回归**。两项失败成因：
- G1/G3/G4/G5/G6/G7/G9/G11：**8 项平衡门禁在 `main` 上本就超标**（属批次 74/75
  经济平衡 v2 的存量门禁问题）；
- T10：`120s` CI 回归防护门禁，本机单局均值 ≈2030ms × 200 局 ≈ 6m46s，**物理上
  无法达标**（机器性能敏感）。

**③ 本批对 `game/virtual_city` 的改动全部是纯新增数据 + 只读 API**，
不触碰月结/校准/MC 路径（`MCRunOneWith` 直调 `World.SettleMonth`，不走
room/`trySettle`/场景注入）。

**结论**：`game/virtual_city` 的 MC 失败项 = **`main` 上的既有问题**（`TestMCSmoke` 的

处置：不修（属独立批次），本批不因此阻塞。
