## 2. 现状诊断（7 个阻塞点）

> 全部结论均来自代码实证，附 `file:line` 引用（行号基于批次 83 之后的 `main` HEAD）。

### 2.1 阻塞点 A —— 场景目录规模天花板被**工具 schema** 卡死

`agent/citysystem/tools.go:74-79` 的 `scenarioKindEnum()` 把**全部场景 kind**
内联进 `inject_scenario` 的 `InputSchema.properties.kind.enum`：

```go
"kind": enumStrSchema(scenarioKindEnum(), "场景 kind(必须来自场景目录)"),
```

101 个 kind ≈ 2.6 KB 尚可；**10,000 个 kind ≈ 260 KB** —— Anthropic 请求体不可接受，
且每次请求都要重传一遍。**这是「支持 10000 种情况」的第一号阻塞点。**

### 2.2 阻塞点 B —— 场景目录规模天花板被**系统提示词**卡死

`agent/citysystem/prompt.go:113-136` 的 `ScenarioCatalogIndex()` 把**全目录紧凑索引**
内联进 `system`。101 条 ≈ 3 KB；1,100 条 ≈ 33 KB；10,000 条 ≈ 300 KB。更糟的是它与
§14.3「三段式头逐字节稳定（全体 Agent 共享 prompt cache 前缀）」直接冲突 —— 目录一变，
前缀就变，缓存全失效。

### 2.3 阻塞点 C —— 目录是**手写 Go 字面量**，无法规模化

`game/virtual_city/scenario.go:174+` 的 `scenarioDefs` 每个条目 ≈ 18 行 Go 字面量。
现有 101 条已拆成 3 个文件（`scenario.go` 10 条 + `batch81` 30 条 + `batch83` 61 条）。
要做到 1,000+ 条 ⇒ 18,000+ 行 Go；做到 10,000 条 ⇒ 180,000 行 Go —— **触碰 §4 单文件
1800 行硬上限并彻底不可维护**（每加一个场景都要改 Go 代码 + 重编译）。

### 2.4 阻塞点 D —— 目录**覆盖维度不足**

现有 6 组（市场与经济 21 / 政策与治理 15 / 社会与舆情 15 / 自然灾害 21 / 未知灾难 16 /
科技与新文明 13）**缺 7 个维度**：公共卫生、基础设施、交通物流、文化教育、环境生态、
公共安全、民生日常。用户逐条列举的 164 个条目中，有 **63 条**在现有目录里找不到对应项。

### 2.5 阻塞点 E —— City-System 工具面不足以支撑「控制一切」

| 缺口 | 后果 |
|------|------|
| 无「目录检索」工具 | 目录上到 1,000+ 后，模型**无法定位**目标 kind |
| `inject_scenario.kind` 是硬 enum | 同 §2.1 |
| 无「指标趋势」工具 | 用户说「最近物价涨得太厉害」→ 只能看**当前值**，无法看**趋势** |
| 无「城区详情」工具 | 注入 `target` 需要真实城区 id，模型只能瞎编（§26「不编造地名」） |

| `send_agent_message` 丢弃返回值 | `dispatch.go:243-253` 调 `hub.Send` 后只回「已发送」——**不是对话** |

### 2.5b 阻塞点 H —— **没有任何 bus handler 按 `msg.Type` 分支**（实证）

全仓 `grep -rn "msg.Type"` 在生产代码里**零命中**（`citybus/bus.go:40` 只是文档注释）。
后果（三条都实测）：

| 现有 handler | 注册点 | 收到 `"message"` 时的实际行为 |
|---------------|--------|------------------------------|
| `City-Chrome` | `main.go:1085-1094` | `msg.Payload.(map[string]any)` 断言失败 ⇒ `category == ""` ⇒ **触发一次全类目采集**，消息正文被丢弃 |
| `City-Human` | `main.go:1099-1104` | 无视 `Type` 与 `Payload` ⇒ 返回**居民摘要**，消息正文被丢弃 |
| `City-WebGL-Show`（房间级） | `ws/game_service_virtual_city_system.go:94-109` | `ParseDisplayRequest` 把字符串 JSON 化再反序列化 ⇒ **类型错误** |

⇒ 批次 81 声称的「Agent 间通讯」实际是**单向空转**。本批的 §4.3 必须**按 `Type`
路由**，且载荷统一为 `map[string]any{"text": ...}`。

同时 `Hub.Agents()`（`bus.go:227-237`）**只列类级** ⇒ 模型看到的 `list_agents` 只有
`City-Chrome` / `City-Human` 两个，**恰恰是忽略 `"message"` 的那两个**；房间级的
`City-WebGL-Show` 反而不可见（它靠 `display.go:27` 的字符串字面量硬编码寻址）。

### 2.6 阻塞点 F —— City-WebGL-Show 只有 6 个显示原语

`agent/citywebgl/tools.go:33-39` 六个原语（focus_district / focus_point / set_mode /

前端已有：消息流 + 工具卡 + 报告卡 + 显示指令徽章（批次 81/83）。
缺：**目录浏览器**（1,000+ 场景无法浏览）、**系统信息面板**、**Agent 来信卡片**。

**关键决策**：

1. **目录规模靠「模板参数化」而不是「手写条目」**：
   模板 = 基础条目 + N 个参数轴（每个轴若干取值），变体由**确定性公式**派生
   （基准 profile × Π轴系数 + Σ轴调整），**零 RNG**。1 个模板可派生 20–150 个变体，
   新增一整个维度只需写 1 个模板 + 轴取值表（纯数据）。
2. **目录不再进 prompt、不再进 schema**：
   - `system` 内联**维度索引**（13 行，每行「维度名 · 条目数 · 代表 kind」）—— 恒定 ≈ 800
     字节，**目录怎么扩容都不变**（保住 §14.3 的 prompt cache 前缀）。
   - `inject_scenario.kind` 改为**普通 string**，枚举移除。
   - 新增 `search_scenarios(query, group, limit)` 作为**唯一**的目录检索入口。
3. **既有 101 条场景语义零改动**：新维度与模板走**新增**文件，目录加载时**合并**
   （kind 冲突时新条目让位给既有条目）⇒ 批次 81/83 的注入语义与预测报告**逐位不变**。
4. **Agent 通讯升级为双向但仍是「一问一答」**：
   `ask_agent`（等回复，带超时）用于对话；`send_agent_message`（不等回复）用于通知；
   新增**上行通道**：任意 Agent `hub.Post(...)` ⇒ System 收到 ⇒ 以 `agent_message`
   事件推给人类 ⇒ 下一轮注入 System 的上下文。**未来新增 Agent 只需 `hub.Register`**
   （§130 合规：无需改 System 代码即可被发现、被呼叫、可回话）。
5. **显示指令扩到 14 原语，但 wire 结构**只加字段不加嵌套**：保持「一条指令 = 一个
   type + 扁平字段」，前端 adapter 逐 type 分派。
6. **零 RNG / 零回归**：模板派生、目录检索、Agent 通讯、显示指令全部是纯函数或
   确定性副作用；场景注入仍复用批次 68 `applyScenarioToWorld`。

#### 4.1.2 模板参数化引擎

```go
// scenario_templates.go
// scenarioTemplate 场景模板:基础条目 + 参数轴 ⇒ 确定性派生变体。
type scenarioTemplate struct {
    Spec     ScenarioSpec     // 基础条目(Kind 为模板基名,如 "pandemic")
    Profile  scenarioProfile  // 基准幅度
    Duration int              // 基准持续月数
    Axes     []scenarioTemplateAxis
}

// scenarioTemplateAxis 参数轴(一个轴 = 一个 kind 后缀维度)。
type scenarioTemplateAxis struct {
    Label  string                  // 轴中文名(如 "病原体")
    Suffix string                  // kind 后缀段(如 "pathogen")
    Values []scenarioTemplateValue
}

// scenarioTemplateValue 轴取值。
type scenarioTemplateValue struct {
    Key    string          // kind 后缀(如 "dengue")
    Label  string          // 显示名(如 "登革热")
    Scale  float64         // profile 整体缩放(缺省 1.0)
    Adjust scenarioProfile // 逐字段加性调整(可只填个别字段)
}
```

**派生公式（纯函数、零 RNG、确定性）**：

```
kind   = base.Kind + "__" + axis1.Suffix + "_" + v1.Key + "__" + axis2.Suffix + "_" + v2.Key …
name   = base.Spec.Name + "·" + v1.Label + "·" + v2.Label …
profile = base.Profile × (v1.Scale × v2.Scale × …)  然后逐字段 += Σ axisValue.Adjust
magnitude  = base.Spec.DefaultMagnitude
duration   = base.Duration
```

**上限保护**：单模板变体数 ≤ `scenarioTemplateMaxVariants = 256`；轴取值数 ≤ 32。

#### 4.1.4 目录检索 API（新增，只读）

```go

func ScenarioCatalogSearch(query, group string, limit int) []ScenarioSpec

// ScenarioDimensionIndex 返回维度索引(分组名 + 条目数 + 代表 kind),
// 供 system 提示词内联(恒定体积,不随目录线性膨胀)。
```

## 11. 风险与回滚

| 风险 | 缓解 | 回滚 |
|------|------|------|
| 目录扩容后 `inject_scenario` 的 kind 校验变慢 | 加载期建 `map[kind]*scenarioDef` 索引（O(1)） | — |
| 目录扩容后 system 提示词膨胀 | **维度索引**内联（恒定 ≈ 800 B）+ `search_scenarios` 外取 | 回退 §4.2 的 kind enum |
| 既有场景语义漂移 | L1 零改动 + 金标准单测（逐字段相等） | 删 L2/L3 文件即可 |
| 前端显示指令类型不全导致「点了没反应」 | adapter 逐 type 实现 + 未实现项显式提示 | 只回退新增 type（旧的 6 个不受影响） |
| Agent 双向通讯引发 LLM 递归 | `ask_agent` **只允许一层**（System → 目标，目标的回包不再触发新的 Agent 调用）；超时 30s | 关闭 `ask_agent` 工具 |
| 指标历史环占用内存 | 环 ≤ 120 条 × 8 float | — |
