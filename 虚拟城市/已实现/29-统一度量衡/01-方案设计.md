## 2. 根因分析

### 2.1 第一层·直接原因 A —— 轴向：按 Y-up 授权，导出后「上」落到 glTF −Z

- 批次 19 的 11 个脚本（civic ×5 / vehicles ×4 / characters ×1 / road ×1）按 **Y-up** 摆放：
  `3d_script/build_vehicle_sedan.py:11` 明文自述「约定：**x=车长方向, y=上, z=车宽方向**」；
  `3d_script/build_pedestrian.py:11` 明文「**y=上**；pivot (0, 0, 0) 在脚下中点；**z 向前为行进方向**」；
  `3d_script/build_city_hall.py:42` 把高度放在位置向量的第 1 位（Blender 的 Y）。
- 但 **Blender 原生是 Z-up**，`bpy.ops.export_scene.gltf` 的 Yup 转换按 `(x,y,z)_b → (x, z, −y)_g` 重映射：
  作者心里的「上」（Blender +Y）⇒ glTF **−Z**；作者心里的「前」（Blender +Z）⇒ glTF **+Y**。
- 后果：three.js 里模型**整个横躺**（高度轴变成水平轴），并且「前进方向」变成竖直轴。
  实测三例印证：`city_hall` 2.00 单位的高落在 Z 上、`comm_tower` 2.30 落在 Y（其"前进轴"竖起来了）、
  `pedestrian_walk` 的长轴 0.860 落在 Z 上（本该是 0.167 的人高）。
- **该陷阱批次 24 已踩过并写明**：`3d_script/build_trash_can.py:19-24` 注释——
  「旧脚本（build_road_props/city_hall 等）按 Y-up 注释摆放，导出后长轴落在 glTF Z 上（侧躺），**本批次不扩散该写法**」。
  即：正确写法早已在库里，只是**没有被回头修**。

### 2.2 第一层·直接原因 B —— 尺度：脚本移植自「1 单位 = 10 m」标准确立**之前**的旧程序化几何

- 世界标尺 `ClientWeb/src/components/virtualCity/cityScale.ts:13` → `METERS_PER_UNIT = 10`，
  即 **1 世界单位 = 10 米**（2026-09-21「3D 高度系统」确立）。批次 19 的脚本（2026-09-23）**早于**该标准生效时的
  「真实米制 → 世界单位」换算纪律，直接照抄了 2.5D 时期以「1 单位 ≈ 1 m」写死的常量：
  - `3d_script/build_vehicle_sedan.py:37` 自述「车身（0.10 长 0.045 高 0.045 宽 ≈ **1m × 0.45m × 0.45m**）」
    —— 作者**有意**造了一辆 1 m 长的玩具车；而前端 `props/Vehicle.tsx:86-91` 的 `VEHICLE_DIMS.sedan.l = 0.45`
    早已写的是 **4.5 m 真车**。**GLB 与 fallback 相差 4.4×**——同一物件的两条渲染路径互相矛盾，这是本批次最硬的证据。
  - 垃圾桶同理：`3d_script/build_trash_can.py:39` `BODY_R, BODY_H = 0.035, 0.09` → 桶径 0.7 m（含盖 0.78 m），
    而真实街边分类桶 ⌀ ≈ 0.5 m。
- 附注：脚本头注释里的「≈ 1m × 0.45m」自述本身就是**单位口径声明**——它写在 2026-09-23，
  即「作者已知这是米制」，但与 2026-09-21 确立的世界单位标尺冲突而**无人核验**（无任何自动校验，见 §2.4）。

### 2.3 第一层·直接原因 C —— pivot：原点在几何中心，消费端不再补偿 ⇒ 半埋

- 批次 19 的 GLB 原点多在模型中心（实测 `minY = −半高`：sedan −0.037 / city_hall −0.420 / comm_tower −1.150）。
- 消费端 `props/Vehicle.tsx:219` 把 group 放在 `y = 0.02`（原为 2.5D 时代"盒底贴地 + 2 cm 抬升"的写法），
  GLB 分支 `<primitive>` 直挂不再补偿（`:292-293`）⇒ 模型一半埋进路面。
- 批次 24 的 `props/RoadsideBins.tsx:81` 已经用「子树包围盒 minY 动态推导抬升」**绕过**该缺陷，
  但那只是**消费端打补丁**，其他 10 个 GLB 没有这层补丁。

### 2.4 第二层·机制原因 —— 规约缺位 + 零自动校验

- 单位 / 轴向 / pivot 三条约定**只存在于实施记录**，从未进入 normative 规约：
  - `../26-坐标系统与城市边缘环境/02-实施记录.md:86-87`：「项目既有 GLB 约定是**世界单位（1 单位 = 10 m）**……
    **消费端零 scale**」——写在**实施记录**里，不是规约。
  - `../26-坐标系统与城市边缘环境/02-实施记录.md:50`：「**新 GLB 轴向规约**：按 Blender 原生 Z-up 摆放导出，
    three.js 里 y 从 0 起、节点 identity，`<Model>` 零旋转直挂」——标题写着"规约"，但实际存在于实施记录。
  - `assets/models/index.ts` 与 `CLAUDE.md §27` 均**无**单位/轴向/pivot 条款。
- `CLAUDE.md §27` 的三条硬约束只覆盖「`.blend` 不入库 / 单 `.glb ≤ 500 KB` / 保留 fallback 三态降级」，
  **没有一条能发现"一辆 1 m 长的车"**——尺寸与轴向走查**全靠人眼**，于是：
  - 批次 26 的「雪山按真实米导出 → 10× 巨山」（`../26-…/02-实施记录.md:83-97`）是同一个坑的**第一次复发**，
    当时**也只是写进实施记录**（新增 `U = 0.1` 常量），**未升级为规约**；
  - 本批次的 11 个旧 GLB 是**第二次复发**（同一根因，不同资产）。
- 结论：**缺的不是知识，是"知识落地为可执行检查"的机制**。本批次的核心产出因此是 §3 规约 + §4 两个自动护栏。

### 2.6 附带发现 —— 一处未被审计覆盖的契约缺口：车辆「正朝向」

审计 §4 的五条判据只校验**直立 / 贴地 / 尺寸 / GLB≡fallback / 节点 identity**，**不含"模型正面朝哪"**。
但尺寸一旦从 1 m 修到 12 m（公交车），朝向错误会立刻变成显性缺陷（12 m 的车横在路上），
因此必须在本批次一并裁定。证据链（三份互相矛盾的证据）：

| 证据 | 内容 | 指向 |
|---|---|---|
| 消费端 yaw 公式 | `props/Vehicle.tsx:193-196` `angle = Math.atan2(dx, dz)`；`props/PedestrianV3.tsx:236` 同式。数学上 `rotation.y = θ` 把局部 `(0,0,1)` 映射到 `(sinθ, 0, cosθ)`，代入 `θ = atan2(dx,dz)` 即 `(dx, dz)/L` = **行进方向** | 模型正面必须 = 局部 **+Z** |
| 批次 18 设计文档 | `../18-3D城市PBR材质与真实城市冲刺/02-架构设计-PBR材质管线与建筑几何深化-v1.md:291-292`：前挡风 `[车身宽×0.85, u(0.28), u(0.04)]`、侧窗 `[u(0.04), u(0.22), 车身长×0.4]` —— **车宽记在 X、车长记在 Z** | 车长沿 **Z** |
| 前端 fallback 实现 | `props/Vehicle.tsx:233-262` 灯/轮/镜/窗常量把「长 = `dims.l`」放在 **X**（`wheelPositions(l,w)` = `[±l*0.32, y, ±w/2]`、前大灯 `x = +l/2`）、`boxGeometry args=[dims.l, dims.h, dims.w]`；palette 六面「前后端 = ±X 面」（`props/Vehicle.tsx:309-317`） | 车长沿 **X**（与上两行冲突） |
| 批次 19 车辆脚本 | `build_vehicle_sedan.py:11`「x=车长方向」+ 前大灯 `x = +0.05`、尾灯 `x = −0.05`、车轮 `z = ±0.025` | 车长沿 X（旧 GLB 实测 X = 0.104 为最长轴，与脚本一致） |
| 批次日志 | `../26-…/02-实施记录.md:48`：「frontend-dev 初版**按车辆 GLB「front=+Z」**设 `rotationY=π/2`；art-designer 的 `build_cargo_ship.py` 实为「+x 为船头」→ 改 `rotationY=0`」 | 团队既有认知是「车辆 GLB front=+Z」，但既有资产实际是 +X |

**裁定（本批次新契约，见 §3.2 R2b）**：统一到 **glTF 原生约定 +Y 上 / +Z 前**（车长沿 Z、**车头 = +Z**）。
理由：(1) glTF 2.0 规范与 three.js 生态的默认正朝向就是 +Z，资产可独立预览；(2) 与消费端既有 yaw 公式
**零改动对齐**（否则要改 `Vehicle.tsx:196` 的 yaw 公式，并波及所有走该组旋转的模型）；(3) 与批次 18 设计文档一致；
(4) 行人脚本的**作者本意**也是「z 向前」（`build_pedestrian.py:11`），取 +Z 可让「车 / 人」两类
yaw 组模型共用同一朝向契约。
代价：前端 fallback 车辆的几何轴序要跟着对调（清单见 §3.2 表下注），这与「GLB ≡ fallback」判据本来就要求两侧同步，
**属于同一次原子修正**而非额外工作量。

## 3. 度量衡规约（本批次核心产出）

> 本节是**唯一事实来源**。任何新增/修改 3D 资产的实现方（art-designer / frontend-dev）先读本节再动手；
> 本节条款变动须同时在 `CLAUDE.md §27`（规约正文）与本文件登记，并同步两侧护栏（§3.6）。

### 3.1 五条硬约定（R1–R5）

| # | 约定 | 判据化（可机械执行） | 出处 / 现状 |
|---|---|---|---|
| **R1** | **世界标尺：1 世界单位 = 10 米**（`u(m) = m / 10`）。所有尺寸常量先写米、再经 `u()` 或 ×0.1 换算；**禁止**在组件内硬编码米制尺寸 | 代码走查 + `REAL_DIMS_M` 表 | `cityScale.ts:13`；本批次**确立为 normative**（原只存在于 `26-…/02:86-87` 实施记录） |
| **R2a** | **GLB 一律按"世界单位"授权**（不是米、不是任何场景 scale 的补偿值）；**Blender 侧按 Z-up 摆放导出**（默认 `export_scene.gltf` 的 +Y up 转换），three.js 侧**节点 identity**、`<Model>` **零旋转零 scale 直挂** | 判据 5（节点 identity）+ 判据 3（尺寸） | `26-…/02:50,86-87`；本批次升为 normative |
| **R2b** | **正面 = 局部 +Z**（glTF 原生 +Y 上 / +Z 前）。被 yaw 组消费的模型（`vehicles/*`、`characters/*`）必须车头/人面前进方向朝 **+Z**；GLB 与程序化 fallback **同向** | 判据 6 | §2.6 裁定；行人脚本作者本意一致（`build_pedestrian.py:11`） |
| **R3** | **pivot 规约：`minY = 0`（底面贴地）+ X/Z 居中**；车辆 pivot 在**轮底中心**、桶/杆/树在**底心**。**唯一例外 = 吃水线类**（`cargo_ship` minY −0.14、`sailboat` −0.05，保持现状） | 判据 2 | 本批次新立（旧 GLB 全部违反） |
| **R4** | **GLB ≡ 程序化 fallback 同尺寸**：同一物件的两条渲染路径包围盒必须一致（±5%）。这是「统一度量衡」的**可测不变量**——fallback 是 GLB 缺失/禁用时的兜底，两者不一致即用户可见的尺度跳变 | 判据 4 | 本批次新立（`disable-blender-models=1` 切换时肉眼可见 4.4× 跳变） |
| **R5** | **真实尺寸表 `REAL_DIMS_M`（§3.4）是尺寸的唯一事实来源**；前端单一尺寸表与 `3d_script` 侧 JSON 镜像为其**副本**，改动须前端 + 美术双侧同步（§3.6） | 判据 3 | 本批次新立 |

### 3.2 轴向与 pivot 细则

**Blender 授权 → glTF/three.js 的轴映射表**（`(x,y,z)_b → (x, z, −y)_g`，Yup 导出）：

| Blender 轴 | glTF / three.js 轴 | 语义 | 授权时怎么摆 |
|---|---|---|---|
| `+X` | `+X` | 世界东 / 模型局部：**右** | 车宽、楼宽、灯排布方向 |
| `+Z` | `+Y` | **上** | **高度放在 Blender +Z**（`make_cylinder` 默认轴 = Z，无需旋转） |
| `−Y` | `+Z` | **前**（正面 / 前进方向 / 车头） | **正面朝 Blender −Y**（= Blender `Numpad 1` 前视图所见的那一面） |
| `+Y` | `−Z` | 后 | 背面 |

> 记忆法：**「Blender 里 Z 是上、−Y 是前，导出即 glTF 的 Y 上 / Z 前」**。
> 反之（把"上"放在 Blender +Y）⇒ 导出后横躺，这正是 §2.1 的 11 个资产。

**pivot 与例外表**：

| 类别 | pivot | minY | 例外 |
|---|---|---|---|
| 建筑（civic ×5） | 底面中心（外轮廓 bbox 的 X/Z 中心） | 0 | — |
| 车辆（vehicles ×4） | **轮底中心**（左右/前后对称中心，Y = 轮胎接地面） | 0 | — |
| 人物（characters） | **双脚落地点中点** | 0 | — |
| 街道家具（road/*） | 底心 | 0 | `road_props` 内 3 杆各自贴地、整体沿 X 排布 |
| 植被（nature/*） | 根部底心 | 0 | `snow_mountain` 为基准地形（前端按需 scale） |
| 船只（ocean/lighthouse 等） | 底心 | 0 | **`cargo_ship` −0.14 / `sailboat` −0.05 = 吃水线**（有意下沉，保持）；`cargo_ship` 长轴 = X（+x 船头，另案特例，见下） |
| 垃圾桶（`road/trash_can`） | 桶底中心 | 0 | 批次 24 时为「原点在桶身中心 + 消费端 minY 补偿」，本批次改 **minY = 0**，消费端补偿随之退化为 0（见 §3.5） |

**`cargo_ship` / `sailboat` 的 +X 船头是"已验收例外"**：二者由 `SouthOcean.tsx` 的巡航动画直接控制
（`rotationY = 0`，+x = 航行方向，`26-…/02:48`），**不经** `atan2(dx,dz)` yaw 组，故不受 R2b 约束。
本批次**不改**（避免回归批次 26 的验收结论）；若将来接线到 yaw 组，须先按 R2b 改授权。

**R2b 的落地面（车辆 fallback 轴序对调清单）**——`props/Vehicle.tsx`：

| 5 | **节点 identity**：`<Model>` 零旋转零 scale 直挂（GLB 根节点 TRS 为 identity） | 解析 GLB JSON 的 `nodes[*].{translation,rotation,scale}` | 带骨骼动画的 `pedestrian_walk`（根为 Armature，允许其内部骨骼变换；根节点仍须 identity） |

> 判据 4 是「统一度量衡」的收口判据——它把「GLB 对了但 fallback 没对」这类**半修**直接判失败。

### 4.2 护栏 1：`3d_script/verify_glb_aabb.py`（资产侧门禁）

- **定位**：art-designer 每导出 1 个 GLB 就跑的**提交前门禁**；纯 stdlib（无 node_modules / 无 Blender 依赖），
  原型见审计用的 `/tmp/glb_world_bbox.py`（手工解析 GLB 的 JSON chunk + 遍历节点 TRS 求世界包围盒）。
- **契约**：
  ```
  cd 3d_script
  python3 verify_glb_aabb.py ../ClientWeb/src/assets/models/vehicles/sedan.glb   # 单文件
  python3 verify_glb_aabb.py --all                                              # 全量回归（读 real_dims.json）
  ```
  - 输出：每个 GLB 一行 `name  X×Y×Z  minY  [PASS|FAIL 原因]`；**表值与实测差 > 5% 即 exit 1**；
  - 判据 1/2/3/5 全在此脚本内实现（轴序、贴地、尺寸、节点 identity）；
  - 数据源 `3d_script/real_dims.json`（§3.4 的 JSON 镜像）——**表与资产不同步即报错**，这就是 §3.6 的堵漏点；
  - 例外清单（`cargo_ship` 长轴 X / 吃水线 / `snow_mountain` 基准）以白名单形式写在脚本内**并注明出处 §4.1**。
- **落地要求**：脚本头注释写明本文件的 §3.4/§4.1 锚点；`--all` 的输出**整段回填** `02-实施记录.md` 的验收表。

### 4.3 护栏 2：前端 `glbSizeGuard`（消费侧护栏）

- **定位**：跑在浏览器里（消费侧），把判据 3/4/5 变成**运行时断言 + 降级**，覆盖「护栏 1 过了但 fallback 没同步」的场景。
- **契约（路径可由 frontend-dev 定稿并登记）**：
  - 位置：`ClientWeb/src/components/virtualCity/glbSizeGuard.ts`（虚拟城市私有，符合 §2.1 硬约束 2）；
  - 输入：已加载的 `THREE.Object3D`（`scene.clone` 前量一次即可，缓存 key = `modelUrl`）；
  - 比对源：`glbDims.ts` 的 `REAL_DIMS_M`（前端副本）；
  - 行为：
    1. `import.meta.env.DEV` 且超差 ⇒ `console.error('[glbSizeGuard] ...')`（含 URL、三轴实测值、表值、偏差比）；
    2. 生产环境**不阻断渲染**，但暴露 `window.__glbSizeReport`（数组，供 integration-tester 一次性取值）；
    3. 偏差 > 2×（如旧资产那种 4.4×）⇒ **强制走 fallback 渲染**（与 §27.3 三态降级链一致），
       宁可显示尺寸正确的程序化几何，也不显示尺度错误的 GLB；
  - 与 `engine3d/modelCache` 的关系：**只在 guard 内量测，不改 `engine3d`**（`engine3d` 禁引游戏私有模块，`CLAUDE.md §2.1-5`）。
- **为什么需要两个护栏**：护栏 1 守**资产出厂**（Blender 侧，无浏览器），护栏 2 守**资产进场**（消费侧，含 fallback 一致性）。
  二者读同一张表（前端副本 / JSON 镜像）⇒ 表是唯一事实来源，护栏是它的两个执行点。
