## 4. 本批的三个工程教训

### 4.1 桥墩压在干道路面上 —— 只有「净距数值解」能防

现状 13 根墩 @ `-30+5i`，其中 x=-25 距 `arterial-z-26` 中心线 1.0 u
（路半宽 0.7 + 墩半宽 0.18 ⇒ **离路缘 1.2 m**）。批次 43~48 的多个事故
（体育场压路、码头伸出城界、桥墩上路）都是同一类：**几何没错，是落位错了**，
而 tsc / 构建 / 出图 / `verify_glb_aabb` 全部无感。

对策是两条：

1. **设计阶段就把落位解出来**（方案 §1.2）：对「N 跨 × 跨距 s，走廊居中」做
   0.005 u 步长网格搜索，判据 `净距 = 点到路段中心线距离 − 路半宽 − 墩半宽`。
   结论是 **30.5 m 是 25~35 m 全区间里唯一可行跨距**（30.0 m 会有一根墩落在路面上，偏差 −0.2 m）。
2. **把判据固化成可重跑的护栏** `scripts/ci/check_rail_corridor.mjs`：
   它 esbuild 出真实的 `roadNetwork` + `VIRTUAL_CITY_DISTRICTS`，
   再从 `RailViaduct.tsx` **源码文本**里取 `SPAN_M` / `PIER_X0` / `PIER_COUNT`，逐墩算净距。
   谁把 30.5 改成 30.0，脚本立刻红。

> 护栏的已知边界：它读源码文本而非 import tsx（tsx 依赖 three/r3f，node 跑不起来），
> 所以**变量改名时脚本会静默取不到值** —— 已在脚本头注释里写明，并让它在取不到时
> `exit(2)` 而不是默默通过。

### 4.2 ★ 单位换算漏一个 `u()`：tsc / 构建 / 出图 / 护栏 全部无感

`RailViaduct.tsx` 里两条 Blender 米 → three 世界单位的换算首版写成：

```ts
const bz = (blenderY: number): number => RAIL_Z - blenderY;   // ✗ 漏 u()
const by = (blenderZ: number): number => blenderZ;            // ✗ 漏 u()
```

后果：列车被甩到 **18 m 外、120 m 高**（根本不在画面里），
程序化 fallback 整体放大 10 倍。**tsc 过、`npm run build` 过、Blender 出图过、
`verify_glb_aabb` 过、`crosscheck` 过、`coverage` 过** —— 六道门禁全绿。

抓住它的是 CDP 里的一句：

```js
o.geometry.boundingBox.clone().applyMatrix4(o.matrixWorld)
```

**只有把世界坐标读回来比对才暴露**。几何表（`REAL_DIMS_M`）比不了，
因为它描述的是 GLB 而不是「Blender 坐标怎么映射到 three」。

> 推广：凡是从建模侧（米）搬到渲染侧（世界单位）的换算，
> 必须有一个断言把两边的**同一件东西**放在一起比。

### 4.3 审计输出「0 / 无穷大」时，先怀疑审计本身

第一版 CDP 脚本报「区间实例 = 0、不同墩位 = 0、走廊包围盒 = 1e9」。
逐行查下来是脚本自己的 bug：

```js
const im = new o.instanceMatrix.constructor();   // ✗ InstancedBufferAttribute
o.getMatrixAt(i, im);                            //   需要 Matrix4
```

`instanceMatrix.constructor` 是 `InstancedBufferAttribute`，
`getMatrixAt` 往它身上 `fromArray` 后 `im.elements` 是 `undefined`，
`e[12]` 抛异常后被外层 `try` 静默吞掉 ⇒ 整段循环白跑。
正解是 `new o.matrixWorld.constructor()`。

（顺带发现：批次 48 脚本里同一行也有这个 bug，只是当时「保留地内实例 = 0」
恰好与期望一致，没暴露。）

**判据**：审计给出「0 / 无穷大 / 完全不匹配」这类**整齐得可疑**的结果时，
先打印中间量确认审计自己跑到了那段代码，再怀疑被测对象。

### 5.1 坐标系（与两支脚本一一对齐）

建模脚本在 Blender 的 **XY 平面**顺走廊铺场（X = 走廊、Y = 横向、Z = 高），
导出 Yup 后 `three.x = Blender.x`、`three.y = Blender.z`、`three.z = -Blender.y`。
⇒ **Blender +Y（声屏障侧 / 出入口塔侧）落在 three 的负 z**，
正对 z = 40 的体育新城与湿地公园（噪声敏感面 + 主要客流方向）。

消费端两个换算 `bz()` / `by()` 是这件事的**单一事实来源**（§4.2 的教训就出在这里，
已在代码里写死注释）。

### 5.2 `RAIL_PIER_LOCAL_X = -1.4115` —— 局部约定必须两侧同步

模块 GLB 的**墩心在局部 x = -1.4115**，不是包围盒中心（包围盒中心是 0）。
实例原点必须落在「世界桥墩位 − 局部墩心」上，否则 20 根墩整体错位 1.41 m。

这个值由 `build_rail_span.py` 收尾时打印（`center_content_xz` 的返回值 = 墩心位移），
消费端写死在 `RailViaduct.tsx` 顶部并带 ⚠ 注释。**护栏管不到这条**（它只管 GLB 自身），
CDP 的 V7b 逐墩比对是唯一防线（实测最大偏差 0.0005 u）。
