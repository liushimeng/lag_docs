## 2. 200 居民 vs 100K 居民：差异点分析

### 2.1 性能差异

| 指标 | 100K（v2.60 默认）| 200（v2.61 推荐）| 加速比 |
|---|---|---|---|
| `TickMonth` 时间 | < 100ms（`city_test.go:124` 断言）| < 1ms（实测 200/100K ≈ 500× 加速）| 500× |
| `Snapshot` 时间 | < 5ms（4096 抽样 + O(N) 聚合）| < 0.1ms（全量 200 < snapshotSampleCap）| 50× |
| 内存常驻 | ≈ 2 MB（100K × 20B）| ≈ 4 KB（200 × 20B）| 500× |
| `PickVoiceCandidates` 时间 | < 1ms（100K 线性扫描）| < 0.1ms（200）| — |
| `voices[]` 环形 | 20 条 | **20 条**（不变）| — |

### 2.2 语义差异

| 维度 | 100K（北京规模）| 200（中等城市）|
|---|---|---|
| "我"的相对地位 | 1/100000（无足轻重）| 1/200（有存在感）|
| 抽样率（4 voice/月）| 0.004% | **2%** |
| 调研问卷合理样本 | 384（95% 置信，5% 误差）| 200 即可（全量）|
| 邻里关系建模 | 不可能 | **可行**（200 人两两关系 = 19900 条）|

### 2.3 UI 差异

100K 居民只能给统计聚合（年龄段 / 收入分位 / 失业率）— 200 居民可以
**全量展开个体卡片**，这是「中等城市」的关键 UX 价值。

## 3. v2.61 的 200 居民优化清单

### 3.1 `TickMonth` 抽样策略（新增）

**问题**：v2.60 的 `TickMonth(cpi, rng)` 是 **全量 O(N)** 演化 —
100K 时这没问题，200 时也"没问题"但**浪费**。

**v2.61 方案**：保留全量演化（确定性 + 单测可断言），但在 200 规模下
新增 **「高保真演化」** 模式：

```go
// backdrop.go 新增（CLAUDE.md §130 验证接线）
//
// HighFidelityTickMonth 高保真月度演化(200 居民场景);
// 复用 TickMonth 的全部规则,额外:
//   1. 每位居民触发"个体事件池"(失业/生病/生育/中奖...)的二次判定
//   2. 个体事件入 city_voice 抽样候选池(提高城市之声的真实感)
//   3. 邻居影响(200 人规模下可行:同城区 ±3 位的 stress 传导)
//
// 仅在 MaxResidents<=1000 时启用;1000 以上回退普通 TickMonth。
// 开关 = (cfg.Wealth.HighFidelityBackdrop = MaxResidents<=1000)
func (b *Backdrop) HighFidelityTickMonth(cpi float64, rng *rand.Rand) {
    b.TickMonth(cpi, rng) // 全量基线
    if len(b.residents) > 1000 {
        return
    }
    b.mu.Lock()
    defer b.mu.Unlock()
    for i := range b.residents {
        // 个体事件(失业/生病/生育/中奖 P<<0.01)
        if rng.Float64() < 0.005 {
            b.residents[i].flags |= flagStressed // 临时压力
        }
    }
}
```

### 3.2 `Snapshot` 聚合（200 < 4096 全量）

**当前**：v2.60 的 `Snapshot` 在 100K 时抽样 4096 算中位数；在 200 时
`len(residents) < snapshotSampleCap` → 已经走全量路径。

**v2.61 优化**：在 200 规模下，`Snapshot` 额外输出 **全量居民 ID 列表**
（供 UI 展开个体卡片）：

```go
// BackdropSnapshot 新增字段
type BackdropSnapshot struct {
    // ... 既有聚合字段
    FullResidentIDs []string `json:"full_resident_ids,omitempty"` // 仅 n<=200 时填充
}
```

**前端**：WealthCityMap 侧栏新增「居民名册」折叠面板（仅 200 规模时显示），
点击居民卡片弹出半弹层显示收入 / 储蓄 / 城区 / 年龄。

### 3.3 `anchorCityProfiles` 档案锚定复用

**问题**：档案锚定（`profile.go`）走 10 万级卡池热替换，200 居民时是否
"过度"？

**答案**：**不优化**。档案锚定是一次性前缀热替换（前 N=200 名映射到
卡池前 200 张）— N=200 vs N=100000 在锚定阶段的代码路径完全一致，
差异只是池大小（仍是 10 万级供后续扩容）。

**v2.61 不动 `profile.go`**，只在 `LsmAgentGame.conf.example` 加注释：

```ini
# 虚拟城市背景居民数(v2.61 推荐 200 = 中等城市)
# 范围 1..100000(防御上限);200 是推荐"中等城市"预设。
# 调大后档案锚定池仍 10 万级,无需额外配置。
max_residents: 200
```

### 3.4 城市之声（`voice.go`）在 200 规模下的调整

**现状**：

```go
// voice.go:32-34
const voicePerMonthMax = 32
// 默认 4 条 / 月
// config.go:1096-1097
if c.Wealth.CityVoicePerMonth == 0 { c.Wealth.CityVoicePerMonth = 4 }
```

**v2.61 推荐**：200 居民下默认调到 **6 条**（不是 4）：
- 4/200 = 2% 抽样率（100K 时是 0.004%，太稀疏）
- 6/200 = 3%（仍然低，但能营造"每月都能听到几条声音"的感觉）
- 上限仍是 32（clamp 不变，运营可按需调）

**新增配置字段**（仅注释 / 默认值变更，不改 schema）：

```go
// config.go:1096
if c.Wealth.CityVoicePerMonth == 0 { c.Wealth.CityVoicePerMonth = 6 }
// ↑ v2.61: 100K 默认 4(0.004%);200 推荐 6(3%) — 数量仍极少,LLM 成本可控
```

**为什么不上 32**：32/200 = 16% 抽样率过高，焦点玩家的"调研问卷"会被
城市之声淹没。6 是「叙事密度」与「焦点玩家主导」之间的平衡点。

### 3.5 与 L1 焦点层的耦合点

| 焦点层动作 | 背景层响应 | 文件 / 行号 |
|---|---|---|
| 焦点玩家买房 | 房价 → 背景居民"租客"切换（stressed ↑）| `actions.go::ActionBuyHouse` |
| 焦点玩家开店 | 周边 200 居民就业 / 消费意愿变化 | `actions.go::ActionOpenShop` |
| 焦点玩家发调研 | 200 居民作为样本池（< 4096 → 全量）| `survey.go::Survey*` |
| 焦点玩家死亡（寿险）| 受益人是「随机一名 200 居民」| `engine.go::EndingAccidentDeath` |
| 城市之声广播 | 焦点玩家可在 chat 侧看到 | `voice.go::Run` → `onRecord` → `event` |

## 4. 200 居民的 4 大 UX 价值

### 4.1 全量个体可见（vs 100K 抽样）

100K 时 UI 只能给聚合统计；200 时 UI 可以展开「王二狗 / 金融CBD / 月入 8500
/ 储蓄 3.2 万 / 已失业 2 月」这种**个体卡片**，玩家点击弹出详情。
这是 v2.60 设计就支持的能力（`Snapshot.FullResidentIDs`），但 100K 时
不应启用。

### 4.2 邻里关系建模

200 居民两两关系 = 19900 条边，UI 可做"邻居图"。 100K 时边数爆炸。
v2.61 在 `HighFidelityTickMonth` 中预留 `b.residents[i].flags |= flagStressed`
的「邻居传导」钩子 — 具体算法 v2.62 阶段 2 实施。

### 4.3 调研样本合理性

社会调研（`survey.go`）的 95% 置信度最小样本 = 384（无限总体）。200 是
**有限总体修正**下的合理样本（n=200 → 抽样误差约 7%，可接受）。
运营可"全民公投"。

### 4.4 「中等城市」叙事

| 城市规模 | 居民数 | 类比 |
|---|---|---|
| 小型 | < 50 | 镇 / 村 |
| **中等** | **200** | **县城 / 大学城** |
| 大型 | 2000 | 中等城市（北京朝阳区）|
| 巨型 | 100K | 首都（直辖市）|

v2.61 把 200 设为推荐预设 = 「县城 / 大学城」级别的中等城市 —
玩家是「1/200 的居民」，比 1/100000 更有存在感，又比 1/12 更有社区感。
