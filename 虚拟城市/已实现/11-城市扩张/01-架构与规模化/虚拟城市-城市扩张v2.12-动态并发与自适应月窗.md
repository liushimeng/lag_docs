## 1. 问题陈述

### 1.1 当前实现的两个"硬编码常量"

v2.60 (`ServerGo/game/wealth/engine.go`) 已落地的两个核心常量：

```go
// engine.go:27-29
// MaxSeats 房间容量(2026-09-16 §12 座扩容:8 → 12,给「1 人类 + 11 bot」
// 留头寸;同时也是精选卡池 / 文档池抽卡张数的硬下限)。
const MaxSeats = 12

// engine.go:35-47
// DefaultAgentConcurrency 是房间级 LLM 并发信号量(agentSem)的默认容量
const DefaultAgentConcurrency = 8
```

注释里说明 8 是 Provider 配额与房间并发间的"平衡点" — 这是手算的，未按
LLM 线路池实际容量自适应。当 v2.61 把"200 居民的中等城市"做成推荐预设时，
运营可能开 2 路 / 3 路 Provider，8 并发会触发 429；同时月窗 (8s/30s)
也是写死的，bot 越多越容易超时。

### 1.2 用户实际场景

| 场景 | Provider 数 | 焦点玩家 | 期望并发 | 期望月窗 |
|---|---|---|---|---|
| 单 Provider 调试 | 1 | 12 | 2（防 429）| 30s |
| 8 Provider 默认 | 8 | 12 | **8（现状）** | 8s |
| 13 Provider 满载 | 13 | 12 | 12（拉满）| 8s |
| 4 Provider 演示 | 4 | 12 | 4 | 12s |

> 核心需求：**并发与月窗要按 Provider 池容量自适应**，而不是"看天吃饭"。

## 2. 设计方案

### 2.1 `DefaultAgentConcurrencyFor(maxSeats, poolTotal)`

**位置**：`ServerGo/game/wealth/engine.go`（与 `DefaultAgentConcurrency` 同文件）

**签名**：

```go
// DefaultAgentConcurrencyFor 返回房间级 LLM 并发信号量(agentSem)的推荐容量。
// v2.61 §动态并发(2026-09-21):按「实际座位数 vs Provider 池容量」自适应。
//
// 公式: target = min(maxSeats, poolTotal, providerQuotaCap)
//
//   - maxSeats: 当前 MaxSeats(本仓库 v2.60 已固化 12,保留不动)
//   - poolTotal: LLM Provider 池可用线路数(取自 llm.Registry.LinePool.Total())
//   - providerQuotaCap: 单 Provider 并发硬上限(默认 2,防止 429 雪崩)
//
// 设计取舍:
//   - 不取 min(maxSeats, 12):保留 maxSeats 入参允许未来扩到 24(下一版审议)
//   - 不取 poolTotal:Provider 自身有全局并发上限,2/probe 是经验值
//   - 下限 floor=1(单 Provider 调试也至少 1 路)
//   - 上限 cap=min(maxSeats, 8)(与 DefaultAgentConcurrency 对齐)
//
// 失败降级: poolTotal<=0 → 返回 DefaultAgentConcurrency(=8)
func DefaultAgentConcurrencyFor(maxSeats, poolTotal int) int {
    if poolTotal <= 0 {
        return DefaultAgentConcurrency
    }
    if maxSeats <= 0 {
        maxSeats = MaxSeats
    }
    // 单 Provider 默认 2 路并发上限(防 429 雪崩,可被未来 audit 覆盖)
    const perProviderCap = 2
    target := maxSeats
    if poolTotal*perProviderCap < target {
        target = poolTotal * perProviderCap
    }
    if target > DefaultAgentConcurrency {
        target = DefaultAgentConcurrency // 上限 8 与原默认值一致
    }
    if target < 1 {
        target = 1
    }
    return target
}
```

**公式与边界**：

| maxSeats | poolTotal | 计算 | 结果 | 备注 |
|---|---|---|---|---|
| 12 | 1 | min(12, 1×2, 8) | **2** | 单 Provider 调试 |
| 12 | 4 | min(12, 4×2, 8) | **8** | 4 Provider 演示 → 拉满 |
| 12 | 8 | min(12, 8×2, 8) | **8** | 默认 |
| 12 | 13 | min(12, 13×2, 8) | **8** | 满载也限 8 |
| 12 | 0 | DefaultAgentConcurrency | **8** | 降级 |
| 12 | -1 | DefaultAgentConcurrency | **8** | 降级 |

### 2.2 `MonthWindowFor(maxSeats, llmConcurrency)`

**位置**：`ServerGo/game/wealth/engine.go`

**签名**：

```go
// MonthWindowFor 返回"决策月窗"推荐时长。
// v2.61 §自适应月窗(2026-09-21):按 (maxSeats / llmConcurrency) 推算,
// 给每批 LLM 决策留 4× 单次决策上限(decisionTimeout=20s)的余量。
//
// 公式: window = ceil(maxSeats / llmConcurrency) * decisionTimeout + buffer
//
//   - decisionTimeout=20s(房间层 NewWealthRoom 注入,manager.go:36)
//   - buffer=4s(网络抖动 + Provider 重试,实测 P99)
//
// 设计取舍:
//   - 12 人 / 8 并发 = 2 批 → 2*20 + 4 = 44s 上限(原 30s 不够 → 调整上限到 60s)
//   - 12 人 / 2 并发 = 6 批 → 6*20 + 4 = 124s(超过 60s 仍 cap 60s,长月窗体验差)
//   - 单人 1 批 → 1*20 + 4 = 24s(下限 floor=8s,避免空房间月窗太短)
//
// 上限 cap=60s(人类玩家等 1 分钟已是体验底线)
// 下限 floor=8s(LLM 调用 P50 < 4s,8s 已够 1 批跑完)
func MonthWindowFor(maxSeats, llmConcurrency int) time.Duration {
    if maxSeats <= 0 {
        maxSeats = MaxSeats
    }
    if llmConcurrency <= 0 {
        llmConcurrency = DefaultAgentConcurrency
    }
    const (
        decisionTimeout = 20 * time.Second
        buffer          = 4 * time.Second
        floor           = 8 * time.Second
        ceiling         = 60 * time.Second
    )
    batches := (maxSeats + llmConcurrency - 1) / llmConcurrency // 向上取整
    d := time.Duration(batches)*decisionTimeout + buffer
    if d < floor {
        d = floor
    }
    if d > ceiling {
        d = ceiling
    }
    return d
}
```

**月窗对照表**：

| maxSeats | llmConcurrency | 计算 | 结果 | 备注 |
|---|---|---|---|---|
| 12 | 8 | ceil(12/8)=2 → 2×20+4 | **44s** | 默认（v2.60 月窗 30s 偏紧） |
| 12 | 2 | ceil(12/2)=6 → 6×20+4 | **60s**（cap）| 单 Provider 长月窗 |
| 12 | 12 | ceil(12/12)=1 → 1×20+4 | **24s** | 满 Provider |
| 1 | 8 | ceil(1/8)=1 → 1×20+4 | **24s** | 单人局 |
| 12 | 0 | DefaultAgentConcurrency=8 | **44s** | 降级 |
| 24 | 8 | ceil(24/8)=3 → 3×20+4 | **60s**（cap）| 24 座未来场景 |

## 3. 为什么保留 12 焦点玩家

### 3.1 三方案的对照

| 方案 | LLM 成本/月 | 触发 429 概率 | 月窗压力 | LLM 决策多样性 | 决策 |
|---|---|---|---|---|---|
| A. MaxSeats=12（v2.61 保留）| 12 | 低 | 24–60s 够 | 中（11 bot 不同 model）| ✅ **采纳** |
| B. MaxSeats=50 | 50 | 中 | 100–200s 紧 | 高（49 bot）| ❌ 体验差 |
| C. MaxSeats=200 | 200 | 高（quarantine）| 400–600s 不可接受 | 高 | ❌ |

### 3.2 「焦点玩家 = LLM 决策者」是硬约束

`engine.go:35-47` 注释明确：12 bot **同时**月度决策 → 4 并发会压成 4 批串行。
`DefaultAgentConcurrency=8` 已经按 12 人的 2/3 设计的（**12/8 = 1.5 批**）。
再增加焦点玩家 → 必须重新设计信号量策略 + 月窗上限 — 这是 v3.0 的事。

### 3.3 「200 居民」如何被 12 焦点覆盖

> 关键洞察：**经济动力 = 焦点玩家；社区肌理 = 背景居民**。

| 维度 | 焦点玩家 (12) | 背景居民 (200) |
|---|---|---|
| 决策 | LLM（每月动作）| 程序化（数值规则）|
| 影响力 | 影响市场价格 / 央行政策 | 影响社区氛围 / 调研抽样 |
| LLM 调用 | 12/月 | 4–32/月（抽样）|
| 关系 | "我"是人类玩家 | "邻居"是 NPC |

200 居民是「中等城市」的人口下限 — 它们的存在是为了让 12 焦点玩家的
「买房 / 租房 / 招聘 / 调研」有真实对象，不是 LLM 决策者。

## 4. 与 §92a 死锁防护的对齐

CLAUDE.md §92a：**`sync.Mutex` 不可重入**，`Action_*` 必须建 `*Locked` 锁内变体。
本次改动涉及 `NewWealthRoom` / `NewCityRoom` 初始化路径（非 `Action_*`），
不触发 §92a，但要确认：

| 改动点 | 是否锁内？| §92a 风险 |
|---|---|---|
| `DefaultAgentConcurrencyFor` 纯函数 | 否 | 无 |
| `MonthWindowFor` 纯函数 | 否 | 无 |
| `agentSem = make(chan, llmConcurrency)` | 否（NewRoom）| 无 |
| `runOneBot` 内部 `case r.agentSem <- struct{}{}` | **是** | 已用 select-default 兜底（`manager.go:437`），无重入 |

**强制要求**：动态化 `agentSem` 容量后，必须保证 `case r.agentSem <- struct{}{}:`
后面的 default 分支（`manager.go:437` 的 fallback）仍能在信号量满时提交。
不能因为动态化导致 fallback 行为变化 — 此项必须有测试覆盖。
