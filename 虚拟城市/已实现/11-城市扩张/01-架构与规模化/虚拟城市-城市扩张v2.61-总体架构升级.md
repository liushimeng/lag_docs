## 1. 为什么升级到 v2.61

### 1.1 v2.60 已实现的现状

v2.60（2026-09-14 §财商流 P0 + 2026-09-21 §档案锚定 + 2026-09-21 §Agent 命名 City 化）已落地：

- **焦点玩家**：`ServerGo/game/wealth/engine.go:29` `MaxSeats=12`，1 名人类 + 11 名 bot
- **背景居民**：`ServerGo/game/wealth/city/backdrop.go` 紧凑数组，理论 `MaxResidents=100000`
  （`config/config.go:1090-1097` 默认 100000）
- **城市之声**：`ServerGo/game/wealth/city/voice.go` 每月抽样 4 条 LLM 短对话
  （默认 4，clamp [0,32]）
- **LLM 调度**：`ServerGo/game/wealth/manager.go:432-438` 的 `agentSem`
  （`DefaultAgentConcurrency=8`，`engine.go:47`）
- **8 城区 + 40×40 地图**：`ServerGo/game/wealth/districts.go:40` `DistrictCount = 8`，
  前端 1 单位 = 10 米（`ClientWeb/src/components/wealth/cityScale.ts:12`）

### 1.2 用户诉求与关键决策

用户希望把虚拟城市做成 **「200 居民的中等城市」**。原计划曾考虑直接把
`MaxSeats` 扩到 200 — 但焦点玩家 = LLM 决策者，200 路并发会让 LLM 成本爆炸
+ Provider 429 + 月窗口被压垮。

**关键决策（修正原计划）**：
**保留 `MaxSeats=12` 不变**（焦点玩家是 LLM 决策者），把「200 居民」理解为
**焦点玩家 (12) + 背景居民 (200)** 的混合架构：

| 层 | 规模 | 决策方式 | LLM 调用密度 |
|---|---|---|---|
| 焦点玩家 | **12** | LLM 每月决策（已有 `City-Player`）| 12 次/月 |
| 背景居民 | **200** | 程序化 TickMonth + 月度抽样 LLM | 4–32 次/月（默认 4）|

> 这是「中等城市」的合理模型：1 名玩家 + 11 bot 主导经济，~200 名背景居民组成社区。
> **「200 居民」= 200 名背景居民**（不是 200 名焦点玩家）。

### 1.3 与「1+11+200」的对齐

| 维度 | v2.60 | v2.61 | 备注 |
|---|---|---|---|
| 焦点座位 | 12 | **12** | 保留 |
| 默认 bot 数 | 11 | **11** | 保留 |
| 默认背景居民 | 100000（防御上限）| **200（推荐预设）** | 推荐下限不是硬上限 |
| 城市之声/月 | 4（默认）| **4–8**（200 规模适配）| 同 |
| LLM 调用/月 | ~12 bot | **~12 bot + 4–8 voice** | +33% LLM 调用 |

## 2. v2.61 双层架构

### 2.1 概念模型

```
┌────────────────────────────────────────────────────────────────┐
│ 虚拟城市 (200 居民的中等城市)                                  │
├────────────────────────────────────────────────────────────────┤
│                                                                │
│  L1 焦点层 (12 座)              L2 背景层 (200 居民)           │
│  ┌──────────────────┐           ┌────────────────────────────┐ │
│  │ 1 玩家 + 11 bot  │           │ 紧凑数组 ≈20B/resident     │ │
│  │ LLM 每月决策      │ ←──影响──→│ 程序化 TickMonth + 月度抽样 │ │
│  │ 工具调用 / 交易   │           │ 城市之声 4–32 条 LLM       │ │
│  │ 焦点玩家 = 经济动力│           │ 背景居民 = 社区肌理        │ │
│  └──────────────────┘           └────────────────────────────┘ │
│            │                                │                  │
│            └────────┬───────────────────────┘                  │
│                     ▼                                          │
│           engine.go World (主时钟 / 央行 / 市场 / 调研)         │
│                     │                                          │
│                     ▼                                          │
│           room.go 房间层 (锁 / 定时 / 广播)                    │
│                                                                │
└────────────────────────────────────────────────────────────────┘
```

### 2.2 双层职责矩阵

| 职责 | 焦点层 (12) | 背景层 (200) | 共享 |
|---|---|---|---|
| **决策** | LLM（City-Player，`agent_runner.go:1015`） | 程序化（`city/backdrop.go:178` TickMonth） | — |
| **数据** | `World` + `*Player` 全字段 | `Backdrop.residents[]` 紧凑数组 | `Ledger` / `Market` |
| **LLM AgentClass** | `LsmAgentGame-City-Player` (`class_names.go:213`) | `LsmAgentGame-City-Voice` (`class_names.go:224`) | — |
| **LLM 调用密度** | 12/月（焦点玩家每人）| 4–32/月（抽样）| 全局经 `llm.LinePool` |
| **工具调用** | 月度 ≤3 工具 + ≤1 speak + submit_month | 无工具（极短对话）| — |
| **广播** | `game.state` (玩家部分) + `game.event` | `city_voice` 事件 + `backdrop.snapshot` | `Hub.BroadcastRoom` |
| **持久化** | `t_lsm_game_wealth_save` | 档案锚定池（10 万级 `anchorCityProfiles`）| — |
| **前端可见** | 焦点 12 座位主视图 | 城市之声侧栏 + 背景统计 | `WealthCityMap.tsx` |

### 2.3 「1+11+200」LLM 调用分工

| 调用方 | 触发 | LLM 成本 | 阻塞月结？|
|---|---|---|---|
| 12 bot 焦点决策 | 月窗 `runOneBot` | 高（工具循环）| 否（信号量排队）|
| 4–32 voice | 月结后异步 `VoiceScheduler.Run` | 极低（无工具）| 否（独立 goroutine）|
| 城市背景画像迭代 | 每月 1 次 | 低 | 否（独立 goroutine）|
| **合计** | — | 12 + 4–32 + 0–1 ≈ **17–45 次/月** | 全异步，月结不阻塞 |

## 5. 关键设计取舍

### 5.1 为什么保留 12 焦点玩家

| 候选方案 | LLM 成本/月 | Provider 风险 | 月窗压力 | 决策 |
|---|---|---|---|---|
| MaxSeats=12（保留）| 12 | 低 | 8 并发 / 30s 够 | ✅ **采纳** |
| MaxSeats=50 | 50 | 中（429）| 25s 月窗紧张 | ❌ |
| MaxSeats=200 | 200 | 高（quarantine）| 100s 月窗仍不够 | ❌ |

12 是「LLM 决策者」的合理上限 — `engine.go:35-47` 注释明确说明：8 并发是 Provider
配额与房间并发的平衡点。再多就是「程序化 NPC」（参见背景居民）。

### 5.2 为什么是 200 背景居民（不是 100K）

- **性能**：100K 居民 `TickMonth` 预算 < 100ms（`backdrop.go:8`），
  但 UI 渲染 100K 居民列表不现实
- **叙事**：200 是「中等城市」的人口下限（vs 北京 2000 万、东京 1300 万）
- **统计**：snapshot 抽样上限 4096（`backdrop.go:31`）— 200 < 4096 可全量计算
- **LLM**：200 居民每月 4–32 条 voice（约 2–16% 抽样）足够营造「城市活气」

> 200 是 **推荐预设**，不是硬上限。`MaxResidents=100000` 不变（防御性上限）。
> 运营可按需调 500 / 1000 / 10000。

### 5.3 为什么地图扩到 80×80（不是 100×100 或 60×60）

| 候选 | 面积 (m²) | 城区容纳 | 缩放比 | 决策 |
|---|---|---|---|---|
| 40×40（保留）| 160K | 8 城区 | 1× | ❌ 拥挤 |
| 80×80 | **640K** | **16 城区** | 1/2× | ✅ **采纳** |
| 100×100 | 1M | 25 城区 | 1/2.5× | ❌ 比例失衡 |
| 60×60 | 360K | 8–12 城区 | 1/1.5× | ❌ 16 城区放不下 |

80×80 = 4 倍面积 = 16 城区 × 8×8 单位（城区底板维持不变）= 缩放比 1/2×，
前端相机距离同步 +1×，避免视觉过空。
