## 1. 背景与目标

### 1.1 欠债是怎么浮出来的

批次 69 做「实时看板统一重构」时，对 `game.state` 视图层做了一次**全量 JSON tag 对账**（口径见 §2）。对账的目的本来是给批次 69 的城市总览面板**取数表**逐字段核名，核着核着发现：**核不上的不是少数，而是成类**。

两类欠债：

| 类别 | 症状 | 为什么长期没被发现 |
|---|---|---|
| **A. 字段名错配** | 前端按 `virtualCity_pct` 读，后端发 `wealth_pct` ⇒ 值恒 `undefined` ⇒ 界面渲染成 0 / 「—」 | **静默失败**：`tsc` 通过（两边各自类型合法）、Go 编译通过、运行时无异常，只是值永远是空的 |
| **B. 契约缺口** | 前端类型里有 `listing_book`、后端视图层**从不下发** ⇒ 面板恒空 | 同上：**声明了却从不接线**（CLAUDE.md §130 的典型形态） |

> 关键教训：**「字段存在」不等于「字段有值」**。本项目里前端类型与后端结构体是两份各自演化的声明，
> 中间隔着 WS 序列化这一层 —— 只要 tag 拼错或压根没接线，两侧都编译通过、运行时都不报错，
> 只有把两侧**逐字**摆在一起比，才能发现「读的是另一个字段」。

### 1.2 根因：批次 21 的全栈重命名误伤

批次 21 做过一次 `wealth → virtualCity` 的**全栈重命名**。重命名工具按标识符前缀匹配，
把 `wealth_pct` / `wealth_score` 一并改成了 `virtualCity_pct` / `virtualCity_score` ——
但**后端 JSON tag 是手写的字符串字面量**，不受 Go 标识符重命名工具保护：

```go
// ServerGo/game/virtual_city/view.go
type WealthLayerJSON struct {
    WealthPct float64 `json:"wealth_pct"`   // ← 后端 tag：真值
}
```

```ts
// ClientWeb/src/types/virtualCity.ts（批次 70 前）
interface VirtualCityPyramidLayer {
    virtualCity_pct: number;                // ← 前端：改名工具改坏的
}
```

重命名只改了**前端**（Go 侧 tag 是字面量，工具不动），两侧就此分叉。批次 21 之后没有做过
视图层的字段级复核 ⇒ **债务累积近 30 个批次**才被批次 69 的全量对账一次性照出来。

### 1.3 本批定位

> **本批 = 结清契约欠债，不是加功能。**

**目标**：

1. **清掉 A 类**（字段名错配）—— 把前端读法统一到后端 tag 真值，界面上恒空/恒 0 的读数全部复活。
2. **清掉 B 类**（契约缺口）—— 后端补齐前端已在消费、后端从不下发的 5 项字段。
3. **补齐前端类型缺口** —— 后端已下发、前端未声明的段（财政 / 产业链 / 金融市场 / 场景推演 / 社会结构新指标）全部声明化。
4. **兑现价值** —— 把结清后的新数据接进城市总览面板，6 组 39 项 → **9 组 61 项**。
5. **立护栏** —— JSON tag 键集合**精确锁定**单测 ⇒ 下次改名再错，CI 立刻红。

**非目标**：

- ❌ 不新增后端业务字段（除 §4 的 5 项契约补全外）。
- ❌ 不改任何 Agent 行为（§4.5 的感知富形状**不回流推理链路**）。
- ❌ 不做「全量重命名清理」—— 历史枚举/键名的死键清理只做**与后端真值直接冲突**的那几处（§7）。
- ❌ 不改批次 69 的看板 IA、目录双源、折叠交互。

## 2. 对账方法论

### 2.1 口径：逐字比对

> **对账的唯一口径 = 后端 JSON tag 字面量 vs 前端 TS 字段名，逐字（byte-wise）比对。**

| 侧 | 事实来源 | 提取方式 |
|---|---|---|
| 后端 | 结构体 tag 字面量 `json:"xxx"` | 遍历 `ServerGo/game/virtual_city/` 下参与 `game.state` 的结构体，抽取 tag 名 |
| 前端 | TS 接口成员名 | 遍历 `ClientWeb/src/types/virtualCity*.ts` 的接口成员 |
| 路径 | 结构化层级 | 后端结构体的嵌套关系 ↔ 前端接口的嵌套关系，**逐层**比对（不只比顶层键） |

**三条比对纪律**：

1. **以 tag 为准，不以 Go 字段名为准** —— 前端读的是 JSON 帧里的 key，不是 Go 的 `WealthPct`。
2. **逐层比对，不只比顶层** —— `payload.asset.min_cny` 这种二级 key 同样要核；本批的 `min_cny` 保密口径就依赖二级核。
3. **枚举值域也要比** —— 键名对了但**值域**错了同样致命（§7 的拍卖类型即此类：键名 `kind` 一直是对的，值域却错位）。

### 2.2 覆盖度

| 维度 | 数量 |
|---|---|
| 后端参与 `game.state` 的结构体 | **73** |
| 后端导出字段（JSON tag）总数 | **501** |
| 前端对应字段（TS 成员）总数 | **399** |

> 覆盖度是**对账覆盖面**的度量，不是「缺陷数」—— 501 个字段里绝大多数逐字一致。

### 2.3 判定四分类

对账结果按「不一致的方向」分四类，**每一类的修法不同**：

| 分类 | 判据 | 修法 | 本批命中 |
|---|---|---|---|
| **① 一致** | tag 与前端成员逐字相同 | 不动 | 绝大多数 |
| **② 后端拼错** | 后端 tag 是笔误（如 `ponzy_ratio`），前端读的是**正确意图名** | **改后端 tag** | `ponzy_ratio` → `ponzi_ratio`（批次 69 已修，本批复用其结论文档） |
| **③ 前端写错** | 后端 tag 正确且语义明确，前端读的是**别的名字** | **改前端读法**（不动后端） | 本批 A 类全部 4 条（§3） |
| **④ 单边缺失** | 一侧有、另一侧无 | 补**缺口小的那一侧**，并考虑是否该补 | 本批 B 类 5 项（§4）+ 前端类型缺口（§5） |

**③ 与 ④ 的边界裁决**：当后端 tag 拼错（②）与前端类型缺失（④）同时命中同一字段时，
**先按 ② 修 tag，再按 ④ 补类型** —— 顺序反了会先把错误的名字固化进前端类型。

> **本批的核心方法论沉淀**：判 ③「前端写错」的前提是**后端 tag 的语义无歧义**。
> 若后端 tag 本身可疑（如 `ponzy_ratio`），不得拿它当基准去改前端 —— 这正是批次 69 §4.1 的教训。

## 3. 错配清单与根因

### 3.1 A 类：前端写错（4 条，后端 tag 为真值 ⇒ 改前端）

| # | 位置 | 前端原读法 | 后端真值 | 症状 | 修法 |
|---|---|---|---|---|---|
| A1 | `VirtualCityPyramidLayer` | `virtualCity_pct` | **`wealth_pct`**（`WealthLayerJSON.WealthPct`） | 财富金字塔三条条宽与百分比**恒为 0** | 改前端字段名 + 消费点（`VirtualCityPyramidPanel`） |
| A2 | `VirtualCityElectionVote` | `virtualCity_score` | **`wealth_score`**（`ElectionVote.WealthScore`） | 市长选举得票明细财富分**恒 `undefined`** | 改前端字段名 + 消费点（`CityStatsPanel`） |
| A3 | `VirtualCityCycle` | `lpr5y` | **`lpr_5y`**（`CycleJSON.LPR5Y`） | 5Y LPR 数值与徽标**恒不渲染** | 改前端字段名 + 消费点（`MarketPanel` 两处） |
| A4 | 顶层 `my_local_pos` | `{x, y}` | **后端从不下发**（坐标在 `my.local_pos`，数组形状 `[x, y]`） | 顶层声明**恒 `undefined`** | **删除**该顶层声明；本人坐标改读 `my.local_pos` |

**A4 特别说明**：这不是「拼错」而是**位置与形状双重错** ——

- 后端坐标在 `MyJSON.LocalPos`（tag `local_pos`，`omitempty`，**数组**形状 `[x, y]`）；
- 前端顶层声明的是 `my_local_pos?: { x: number; y: number }`（**对象**形状）；
- 且**后端顶层从来就没有 `my_local_pos` 这个 key**。

⇒ 前端声明的是一个**从未存在过的契约**。修法不是「把它挪到 `my` 下」，而是
**删掉假契约 + 在 `VirtualCityMyState` 上补 `local_pos?: [number, number]`**（同时补 `bot_contexts[].local_pos`，后端 `BotCtxJSON.LocalPos` 早已下发但前端未声明）。

### 3.2 枚举值域错位（1 条，见 §7）

| # | 位置 | 前端原值域 | 后端真值 | 症状 |
|---|---|---|---|---|
| A5 | `VirtualCityAuctionKind` | `english \| sealed \| take_it \| single_round` | **`english \| sealed \| dutch \| vickrey`**（`AuctionType`） | ① `dutch`/`vickrey` 拍卖**无 i18n 标签**（渲染成裸 key）；② `take_it`/`single_round` 是**永不命中的死键** |

### 3.3 根因小结

| 根因 | 表现 | 本批对策 |
|---|---|---|
| **批次 21 重命名误伤** | tag 是字面量，不受 Go 标识符重命名保护 ⇒ 前后端分叉 | §3.1 全部改前端；**护栏**：JSON tag 键集合精确锁定单测（§8） |
| **前端自造枚举** | 枚举值域不对齐后端常量 | §7 逐字对齐 + 死键清理 |
| **跨端枚举无单一事实来源** | 后端 `AuctionType` 有常量定义，前端另写一份字面量联合 | **本批仍留缺口**（§9 L5）：后续考虑后端下发枚举值域目录 |

> **不改后端的理由**：A1–A4 中后端 tag 的**语义无歧义**（`wealth_pct` 就是「占总财富比例」，
> `wealth_score` 就是「财富排名分」，`lpr_5y` 就是「5 年期 LPR」），
> 且后端 tag 已被**其它文档与数据库口径**引用 ⇒ 改后端会引入新的分叉面，不划算。

## 4. 契约补齐设计（后端 5 项）

> 5 项的共同形态：**前端已在消费（类型已声明 / 面板已画），后端视图层从不下发**。

### 4.1 `game.state.listing_book` —— 房间挂单簿

**语义**：房间级交易快照，挂单 / 议价 / P2P 借贷 / 拍卖四张表。

**结构（与前端 `VirtualCityListingBook` 逐字对齐）**：

```
listing_book
├── listings[]   → ListingJSON        (id/type/seat/payload/ask_cny/status/create_month/expire_month)
│   └── payload  → { asset | loan | info }   （三类互斥，未用分支 omit）
├── negotiates[] → NegotiateSessionJSON
├── p2p_loans[]  → P2PLoanJSON
└── auctions[]   → AuctionJSON
```

**落地**：新文件 `ServerGo/game/virtual_city/view_trade.go`（419 行）——
**`game.state` 挂单簿的唯一实现**，不改既有交易逻辑，只做「读取 + 视图化」。

**四条口径（硬约束）**：

| # | 口径 | 说明 |
|---|---|---|
| ① | **底价 / 保留价仅卖家本人可见** | `payload.asset.min_cny` 与 `auction.reserve_cny` 只在 `viewer == 卖家座位` 时下发；其余视角**连键都不出现**（`omitempty`）⇒ 非卖家帧内 `strings.Contains(json, "min_cny")` 为假。设计稿口径：「公开信息，不公布底价」 |
| ② | **密封 / 维克里拍卖开标前不下发出价金额** | `sealed` / `vickrey` 进行中 ⇒ `bids` 下发空数组；已开标（`status != active`）才下发金额 |
| ③ | **只下发「活的」条目** | `listings`: `status ∈ {open, negotiating}`；`negotiates`: `status = active`；`p2p_loans`: `balance_cny > 0`；`auctions`: **全部**（含已结束，`AuctionModal` 要回看最后一场） |
| ④ | **四个数组恒为 `[]` 而非 `null`** | 空房 / 无交易 ⇒ `emptyListingBookJSON()` 兜底 ⇒ 前端 `.map` / `.length` 不炸；且**不会残留上一局的旧数据**（store 种子 `state?.listing_book ?? s.listingBook` 会拿到空数组而非 `undefined`） |

**额外口径**：

- **稳定排序**：房间级 map 迭代序随机 ⇒ 必须排序，否则每帧顺序抖动。排序键用
  「数字后缀补零 + 原始 id」（`L2 < L10`，避开字典序坑）。
- **不下发的字段**：信息挂单的明文详情 `Detail`、暗标出价记录 `Bids` —— 前端类型无对应字段 ⇒ 不下发（只发 `detail_hash`）。

**单测断言点**（`view_contract_batch70_test.go`）：

- 资产挂单：字段齐备 + **非卖家帧内不得出现 `min_cny` 键**（`strings.Contains` 断言）+ 卖家帧内须出现 `"min_cny":4000`。
- 借贷挂单 + 议价会话：能按 id 命中。
- 空房：四个数组非 `null`。
- 拍卖保留价：仅卖家可见。
- 密封拍卖：进行中 `bids` 为空。

### 4.2 `game.state.early_repay_eligible` —— 提前还款入口资格

**语义**：本人是否存在**可提前还款**的房贷。

**口径**：

| 项 | 裁决 |
|---|---|
| 判定谓词 | **复用** `actEarlyRepay` 的既有谓词（`loanEarlyRepayEligible`：仅房贷 + 余额 > 0）⇒ 抽取为**共享函数** `loanEarlyRepayEligible(l *Loan) bool` / `hasEarlyRepayEligibleLoan()`，动作与标记**同一份口径**，杜绝两处漂移 |
| 是否含「动作预算」 | **不含**。预算是**本回合**的临时额度（耗尽当回合不可用），不该让「提前还款」入口**整月消失** ⇒ 动作本身仍由 `actEarlyRepay` 拒绝（预算/违约规则各自判定） |
| `omitempty` | **不带**（总是下发）。前端 `ActionPanel` 用 `!!gameState?.early_repay_eligible` 判显隐，缺字段与 `false` 同义，但显式下发更利于排障（观战者 / 无房贷恒 `false`） |
| 观战者 | 恒 `false` |

**单测断言点**：有房贷且余额 > 0 ⇒ `true`；消费贷 / 无贷 / 余额为 0 ⇒ `false`；观战视角 ⇒ `false`。

### 4.3 `my.savings_deposit` —— 定期存款（接线缺口）

**语义**：P1 M2 口径的定期存款余额。

**根因**：§130 的典型形态 —— `MyJSON.SavingsDeposit`（tag `savings_deposit`）**声明了却从不赋值**，
`myJSONFor` 构造 `MyMy` 时漏了 ⇒ 前端 `my.savings_deposit` 恒 `0`。

**修法**：`myJSONFor` 补 `SavingsDeposit: p.SavingsDeposit` ⇒ `jsonMy` 透传。

**单测断言点**：给玩家设定期存款 ⇒ `my.savings_deposit` 与 `p.SavingsDeposit` 相等。

### 4.4 `cycle.minsky_moment_count / ponzi_count / ponzi_ratio` —— 明斯基三字段

**语义**：明斯基时刻触发次数 / 庞氏族人数 / 庞氏族占比。

**口径 —— 单一事实来源**：三个值**全部取自同帧的 `minsky_overview`**（`MinskyOverview`），
**不另算**（避免两处口径漂移；`BuildClientState` 里 `cs.Cycle.MinskyMomentCount = cs.Minsky.MomentCount` 一行即接线）。

> ⚠ 注意 `cycle.ponzi_ratio` 与 `minsky_overview.ponzi_ratio` 的 tag **同形但不同源**：
> 前者是 `CycleJSON.PonziRatio`（本批新增），后者是 `MinskyOverview.PonziRatio`（批次 69 修正拼写）。
> **同形不同源是隐患** —— 本批以「同帧同源赋值」消解，但建议后续把 `cycle` 段的明斯基字段改为**引用**而非复制（§9 L4）。

**单测断言点**：`cycle.minsky_moment_count == minsky_overview.moment_count`（逐值相等，锁死同源）。

### 4.5 `bot_contexts[].last_senses[]` —— 居民感知富形状

**语义**：本月感知记录的**结构化**内容（人 / 物 / 事 / 声 / 味）。

**现状**：`SenseResult` 早已由 see / hear / smell 工具产出同形数据，但 `recordSenseLocked`
**只把「人读摘要文本」存进 transcript** ⇒ 前端 `VirtualCityBotPanel` 的「感知」小节恒空
（读不到 `people` / `things` / `events` / `utterances` / `smells` / `sounds`）。

**修法**：`recordSenseLocked` 增加 `res *vctypes.SenseResult` 形参，把富字段一并落到
`SenseEntry`（`district` / `people` / `things` / `events` / `utterances` / `smells` / `sounds`，
未用的分支 omit）。

**两个关键约束**：

1. **不改任何 Agent 行为** —— `last_senses` **只进 `game.state` 视图层**，**不回流 Agent 推理链路**
   ⇒ 不新增提示词字段、不改工具返回、不改 `See`/`Hear`/`Smell` 的对外语义。
   （`recordSenseLocked` 的 `res == nil` 分支保持旧行为，向后兼容。）
2. **`people[].seat` 必发** —— `vctypes.NeighborBrief.Seat` 带 `omitempty` 会把 **0 号座位吃掉**

### 6.3 三个单位口径坑（**本批最易踩的三个**）

| # | 字段 | 真实语义 | ❌ 错误做法 | ✅ 正确做法 |
|---|---|---|---|---|
| 1 | `treasury.public_service_idx` | **点数**：每累计投入 1 万元 +1 点，**上限 100**（后端 `fiscal_policy.go` 的 `PublicServiceIdxUnit` / `Max`） | 用 `formatPct` 渲染成「37.5%」 | 按**点数**渲染（`num(x, 1)`）—— 百分比读数会把「公共服务投入 37.5 万元」误读成「服务质量 37.5%」 |
| 2 | `supply_chain.price_idx` | **基期 1.0 的价格指数**（Tier 0–3 各一档） | 用 `formatPct`（会显示成「103.2%」） | 按**指数**渲染（`num(x)`）—— 与股票指数 / 房价指数同款口径 |
| 3 | `scenarios_recent` | 后端**可能下发 `null`**；**存在但为空数组**是合法的「还没注入过场景」 | 空数组显示「—」 | **字段存在（含空数组）⇒ 显示 `0`**；**字段缺失（`undefined`/`null`）⇒ 显示「—」** |

> 第 3 条的判据在实现里是显式的三态：
> `scenarios_recent === undefined || scenarios_recent === null ? '—' : cnt(scenarios.length)`。
> 理由：批次 69 已确立「缺失一律显示『—』，0 与『无数据』语义不同」；
> 但**空数组是「确知为 0」**，与「字段缺失」不是一回事 ⇒ 这里必须分三态，不能一刀切。

### 6.4 渲染纪律（沿用批次 69 §7.1）

- 缺失值一律「—」，**绝不渲染 `undefined`**。

- `gameState === null` ⇒ 既有空态块，**不崩溃**。

## 7. 枚举治理

### 7.1 `AuctionType` 对齐

**后端真值**（`ServerGo/game/virtual_city/auction.go`）：

```go
AuctionEnglish AuctionType = "english" // 英式公开叫价
AuctionSealed  AuctionType = "sealed"  // 密封暗标
AuctionDutch   AuctionType = "dutch"   // 荷兰式降价
AuctionVickrey AuctionType = "vickrey" // 维克里(二价密封)
```

**前端原值域**：`'english' | 'sealed' | 'take_it' | 'single_round'` —— 两个方向都错：

| 问题 | 后果 |
|---|---|
| `dutch` / `vickrey` 缺失 | 后端真实下发这两种类型时，`AuctionModal` 的 `t(\`virtualCity.auction.${auction.kind}\`)` 渲染成**裸 key**；徽标类 `virtualCity-badge--auction-<kind>` **无配色** |
| `take_it` / `single_round` 是死键 | 后端从不下发 ⇒ 对应 i18n 键是**永不命中的死键**；CSS 类同理为**死样式** |

**处置**：

1. 前端类型改为 `'english' | 'sealed' | 'dutch' | 'vickrey'`（**逐字对齐后端常量**）。
2. i18n 键 `virtualCity.auction.takeIt` / `.singleRound` ⇒ 改为 `.dutch` / `.vickrey`（三语言同步，`virtualCityP2-{zh,en,ja}.ts` + `virtualCityKeys.ts` 类型面）。
3. CSS **新增** `.virtualCity-badge--auction-dutch` / `--auction-vickrey` 两条配色（**§26.3 三件套**：类名与 JSX 同提交）。
4. **不做语义映射**：`dutch`（荷兰式，逐月降价）与 `take_it`（二手一口价）**语义不同** ⇒
   绝不能把旧键改名成「看起来像」的后端类型（那会把历史语义说错）。**以改键而非映射解决**。

### 7.2 死键 / 死样式清理

| 对象 | 处置 | 理由 |
|---|---|---|
| i18n `virtualCity.auction.takeIt` / `.singleRound` | **改名**为 `.dutch` / `.vickrey` | 死键 ⇒ 键位复用（键集总数不变） |
| CSS `.virtualCity-badge--auction-take_it` / `--single_round` | **保留**（注释标注为历史残留死样式） | CSS 类名不是字段契约；「改名 + 保留」会留下一条无主样式，**新增两条 + 注释标注**是更小风险的做法（§9 L6 建议后续彻底清） |
| 前端 `VirtualCityAuctionKind` 值域 | **改**（唯一真值） | §7.1 |
