## 1. 缺陷陈述

### 1.1 规范要求

glTF 2.0 规范（§3.9 Materials）：

> `pbrMetallicRoughness.baseColorFactor` — The factors for the metalness and roughness of the material... **all linear**.

同章 `emissiveFactor` 亦为**线性**量（`KHR_materials_emissive_strength` 的 `emissiveStrength` 是其倍数）。

### 1.2 实测（开工前核对，非推断）

直接读 `civic/substation.glb` 的 JSON chunk：

| 材质 | 库中 `baseColorFactor` | `CITY_PALETTE` 对应 hex | 该 hex 的 **sRGB** | 该 hex 的 **线性**（正确值） |
|---|---|---|---|---|
| `Substation_Concrete_Mat` | `(0.7137, 0.7020, 0.6784)` | `concrete = #b6b3ad` | `(0.714, 0.702, 0.678)` | **`(0.468, 0.451, 0.418)`** |
| `Substation_Steel_Mat` | `(0.5529, 0.5804, 0.6118)` | `steel = #8d949c` | `(0.553, 0.580, 0.612)` | **`(0.266, 0.296, 0.332)`** |
| `Substation_Vent_Mat` | `(0.2471, 0.2706, 0.2980)` | `vent_louver = #3f454c` | `(0.247, 0.271, 0.298)` | **`(0.050, 0.054, 0.063)`** |

⇒ 库中存的是**把 hex 除以 255 的 sRGB 数值**，被 glTF 规范当作线性值读取。

### 1.3 根因

`__common__.py` 的路径只有一处：

```python
def _hex_to_rgb(hex_str):  # '#rrggbb' → (r/255, g/255, b/255)   ← sRGB 值
    ...
bsdf.inputs['Base Color'].default_value = (r, g, b, 1.0)          # ← 直接塞进去
```

`CITY_PALETTE` 里的每个 hex 都是**设计师按屏幕观感挑的 sRGB 值**（这是对的、
也是色板该有的样子）；Blender 的 Python API 对 `default_value` **不做任何转换**，
于是 sRGB 值被当作线性值存进 shader。

### 1.4 渲染后果

three.js 按线性值做光照与输出编码 ⇒ **整城提亮一档**：

| 物件 | 期望观感 | 实际渲成 |
|---|---|---|
| `tire = #1c1e22`（近黑橡胶） | 轮胎是画面里最暗的件之一 | **中灰** |
| `traffic_signal.signal_housing = #17191d`（灯箱近黑） | 灯箱壳应是剪影 | **浅灰** |
| `asphalt = #3f4247` | 沥青路面是深灰 | **水泥灰**（线性应为 0.05，实际 0.25） |
| `container_red = #8f4a38` | 锈蚀暗赭 | 偏粉的砖红 |

批次 44 是**出图判读**时第一次撞见它（当时记为「轮胎渲成中灰、信号灯壳渲成浅灰」），
但当时无法确认是资产问题还是渲染管线问题，于是登记为遗留。批次 51 用上面的
实测把因果链闭合。

### 1.5 为什么此前**六次**登记都没修

| 原因 | 说明 |
|---|---|
| **改一处就要重导 72 件** | 单件 4~41 s，全量约 6~8 分钟，而任何一批只做 1~3 件 |
| **改一处就要重判 6 个批次的出图** | 批次 41~50 的视觉判断（"比 X 暗一档"）都是在**错误渲���**下做的 |
| **`make_material` 是全局入口** | 没有「只对新资产线性化」的开关，要么全改要么不改 |

三条合起来使它长期挂着 —— 直到批次 51 有了一个**必须重跑每一个脚本**的理由（§4）。

## 2. 方案

### 2.1 换算入口（唯一）

`__common__.py` 新增：

```python
def srgb_to_linear(c: float) -> float:
    return c / 12.92 if c <= 0.04045 else ((c + 0.055) / 1.055) ** 2.4
```

`_hex_to_rgb(hex, linear=True)` 默认走换算，**全部 72 个生成器无需改一行** ——
这是把修复收敛成一个函数而不是 72 次改动。

### 2.2 同步要换算的第二个量：`emissive`

`emissiveFactor` 同样是线性量。不换算会让夜景整体塌一层
（如站名牌蓝 `#1a4f9c`：sRGB 0.10 vs 线性 0.028，**差 3.5 倍**）。

**风险**：批次 41~50 的夜间自发光目标值（`litMaterials` 里的 1.2~3.0）
全是在「emissive 存 sRGB」前提下调出来的，换算后可能偏暗。
⇒ 交付前必须 CDP 实测夜景（§6 V9）。

### 2.3 全量重导

新增 **`scripts/ci/reexport_all_glb.sh`**：按类别枚举 72 件，
逐个 `blender --background --python build_<X>.py -- <目标路径>`。
多输出脚本（`build_vehicle_sedan` → 附产 `sedan_silver`、
`build_vehicle_truck` → 附产 `truck_white`）从输出路径推 sibling，只需给主产物传路径；
`build_character.py` 走 `--archetype` / `--variant` 两参（8 原型 + 15 变体）。

脚本支持传入输出根目录（默认原地），可先导到临时目录做 A/B 对比。

本批**不新增/不改任何 `REAL_DIMS_M` 条目**（颜色不影响几何）。
沿用并全量重跑：

## 4. 触发本批的那件事：脚本与资产早已脱节

批次 51 必须重跑**每一个**生成器，重跑后 `verify_glb_aabb.py` 立刻报：

```
✗ FAIL  贴地：minY = -0.2500（应为 0）            ← nature/oak_tree
✗ FAIL  尺寸 Y：实测 0.5000 目标 1.010（+50.5%）  ← nature/oak_tree
✗ FAIL  尺寸 Z：实测 0.8100 目标 0.470（+72.3%）  ← nature/oak_tree
```

`build_oak_tree.py`（批次 19 原版）导出的是**横躺**的树，而库里的
`oak_tree.glb` 是**批次 29「统一度量衡」单独修好的直立版** ——
**脚本与资产早就不是同一个东西了**，但没有任何判据检查「用当前脚本重跑
能否复现库里的资产」。

批次 44 写 `build_oak_tree_season.py` 时已发现并修正，其文件头原话：
「批次 19 的 oak_tree 侧躺（Blender 内 x∈[-0.25,0.25] / z∈[-1.01,-0.2]），
本脚本改为 Z-up 修正该缺陷」，且 `VARIANTS` 带 `'oak_tree': 'summer'`
（「原版绿；用于（可选）修正批次 19 的 oak_tree.glb」）——
**那个「可选」在批次 51 变成了必做**。

处置：
1. `oak_tree.glb` 改由 `build_oak_tree_season.py` 导出（stem `oak_tree` → `summer`）；
2. `build_oak_tree.py` 文件头加**废弃告示**，正文保留作历史留档；
3. `reexport_all_glb.sh` 里 `oak_tree` 走 season 脚本并写明理由。

## 7. 明确不做

1. **把 `CITY_PALETTE` 整体重新调色** —— 换算后个别颜色（如沥青）偏暗，
   后续可用「按渲染结果微调 hex」的方式单件优化，但那是逐件的美化，
   不属于「修规范错误」。
2. **纹理贴图的 sRGB 标记** —— 本仓库 GLB 全是纯色 PBR、无贴图；
   将来有贴图时需另设 `image.sRGB` 标记。
3. **「脚本可复现性」护栏**（重跑脚本比对包围盒）—— 见实施记录 L1，代价是每次门禁跑 N 次 Blender。
