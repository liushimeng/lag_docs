# 批次 64 · 认证持久化废弃选项清理 · 方案与实施记录

> 日期：2026-10-20 ｜ 分支：`main`（§10.1）
> 起因：批次 61 视觉验收时构造「刷新后登录态」用例，实测发现每次刷新都会弹登录框。
> 排查后**确认不是应用 bug**（见 §2），但顺着这条线发现一个真实缺陷。

---

## 1. 实测结论：「刷新掉登录」是**误报**

构造用例时把 JSON 对象字面量直接拼进 CDP 注入脚本：

```js
localStorage.setItem('lsm.auth', {…})   // ✗ 对象被 String() 成 "[object Object]"
```

`localStorage` 只存字符串 ⇒ 键值被写成 `'[object Object]'` ⇒ 应用正确判定为损坏键并走未登录路径。
**换成 `JSON.stringify(obj)` 后，未改动的应用刷新后 token 完好、不弹登录框、无告警。**

⇒ **结论：`lsm.auth` 的持久化此前一直是好的**，不需要修。
（这条结论很重要——否则会在没有 bug 的地方「修」出一个回归。）

## 2. 真实缺陷：`deserialize` 走的是 zustand 已废弃的 `oldImpl`

`ClientWeb/src/store/auth.store.ts` 的 `persist` 配置里有自定义 `deserialize`
（2026-09-28 提交 `a6197523fe` 为修「lsm.auth 损坏 ⇒ 全站黑屏」而加）。
读 `ClientWeb/node_modules/zustand/esm/middleware.mjs` 源码确认：

```js
// persistImpl(第 571~578 行)
if ("getStorage" in baseOptions || "serialize" in baseOptions || "deserialize" in baseOptions) {
  console.warn("[DEPRECATED] `getStorage`, `serialize` and `deserialize` options are deprecated…");
  return oldImpl(config, baseOptions);   // ← 走旧实现
}
return newImpl(config, baseOptions);
```

| 事实 | 影响 |
|---|---|
| `oldImpl` 用 `getStorage: () => localStorage`（**原始字符串**），`options.deserialize(str)` 收到的就是字符串 ⇒ 功能正常 | 当前无 bug |
| 但每次页面加载都会打 `[DEPRECATED]` 告警 | console 噪音，且**掩盖真正的错误** |
| `oldImpl` **静默忽略 `storage` 选项** | 将来若有人补一个 `storage:` 会是**死代码**（§130） |
| **zustand v5 移除了 `deserialize`** | 一旦升级，回退到 `createJSONStorage`，其 `getItem` 的 `JSON.parse` **无 try/catch** ⇒ 损坏键同步抛错 ⇒ persist 链尾 `.catch` 吞错 ⇒ `hasHydrated` 永假 ⇒ **全站黑屏** |

⇒ 也就是说：`a6197523fe` 想防的那个黑屏场景，在升级到 zustand v5 时会**原样复现**。

## 3. 修法

改为**自定义 `storage` 承载「读时容错」**，并删掉废弃的 `deserialize`：

| 文件 | 改动 |
|---|---|
| `src/store/authStorage.ts` | **新增**（100 行）：零依赖 `PersistStorage`。`getItem` 在 try/catch 里 `JSON.parse`，失败时打印准确告警、`removeItem` 清坏键、返回 `null`（**不抛**）；`setItem`/`removeItem` 吞掉配额/隐私模式错误 |
| `src/store/auth.store.ts` | 改用 `storage: safeLocalStorage`；**删除** `deserialize` ⇒ zustand 走 `newImpl`，真正使用我们的 storage。`partialize` 字段集合 / `onRehydrateStorage` / `App.tsx` 的 1500ms 超时兜底闸门**全部不变** |
| `scripts/verify_auth_persist.mjs` | **新增**：12 条断言回归脚本（真实 zustand 4.5.7 + 真实 storage 模块，走 `newImpl` 路径；另加源码级断言防 `auth.store.ts` 悄悄退化） |
| `package.json` | 新增 `"verify:auth-persist"` |

**为什么这样仍不黑屏**：坏键在 `getItem` 里就被捕获并清除、返回 `null` ⇒
persist 走「无持久化状态」成功路径 ⇒ `hasHydrated` 正常置位 ⇒ `App.tsx` 闸门放行。

## 4. 验收（实际输出）

- `npx tsc --noEmit` ✅ ；`npm run build` ✅（`✓ built in 16.72s`）
- `npm run verify:auth-persist` ⇒ **12/12 通过**：
  - (a) 合法 `{state:{token:'tk-abc',…},version:0}` ⇒ rehydrate 后 `token === 'tk-abc'`、
    `isAuthenticated === true`、`hasHydrated === true`，且持久化 blob **不被空状态覆盖**；
  - (b) 损坏串 `'[object Object]'` ⇒ **不抛错**、`hasHydrated === true`、store 回到默认（未登录）、坏键被清除；
  - (c) 源码断言：`storage: safeLocalStorage` 存在、废弃 `deserialize` 不存在、`onRehydrateStorage` 保留。
- **真实浏览器**（headless Chrome + CDP，Vite dev server :39003）：
  - 合法状态 ⇒ 刷新后 `token` 完好、`isAuthenticated: true`、**无登录框**、**无 `[DEPRECATED]` 告警**；
  - 毒化键 ⇒ 刷新后应用完整渲染（**不黑屏**），console 打印准确的
    `[auth] lsm.auth 内容损坏（非法 JSON），已清除该键并按未登录启动`，坏键自愈为默认态。
- 隔离用的 Vite dev server 与 Chrome 进程**均已清理**，无残留。

## 5. 遗留 / 建议

- 若日后升级 zustand 到 v5，`authStorage.ts` 是唯一的适配点（已就位，无需再改）。
- 其它 store（`ui.store` / `i18n.store` / `connection.store` 等）**未做同样清理**；
  它们没有自定义 `deserialize`，走 `newImpl` + `createJSONStorage`，
  遇到损坏键会同步抛错并可能卡住 hydration 闸门。建议后续批次统一加同款安全 storage。
