## 2. 关键实现决策

### 2.1 「替换」而非「叠加」（方案 §3.2 落地）

`FreeViewControls` 一个组件持有三种模式的内部状态，`useFrame` 里按当前模式分派到对应积分器
（`stepOrbit` / `stepFly` / `stepWalk`）。因此：

- 模式切换不再需要「卸载 A + 挂载 B」，`FocusLerpController` 的职责被吸进同一个组件
  （都改 `target`），两个旧文件一并删除 —— 不留第二套实现，避免 §130 意义上的「僵尸分支」；
- 过渡状态机只需要处理**相机位姿**（pos + quat + fov）一个量，与模式内部参数解耦。

### 2.2 Seed 而非重置（方案 §8.2 落地）

实测 orbit → fly 时相机位置**逐分量不变**（`[10, 16.5, 51.2]` → `[10, 16.5, 51.2]`），
fly → orbit 也保持视线方向不变、只改约束方式。`R` 键才是真正回到 home 位姿。

### 2.3 三态各有基速

`FreeViewControls` 的 `speed` 若三态共用，街景漫游会变成 20 m/s 狂奔。故拆成
`speed`（飞行 20 m/s）/ `orbitPanSpeed`（俯瞰平移 10 m/s）/ `walkSpeed`（街景 1.5 m/s），
档位与 `Shift` 加速在三者之上正交相乘。

### 2.4 楼高公式上提（方案 §6.2 落地）

`DistrictBuildings` 与 `freeViewColliders` 都要「某栋楼有多高」。复制公式就会在下次改渲染时
漏改碰撞（相机穿楼或被空气挡住）。故把 `prosperityOf` / `buildingTopY` 上提到 `cityScale.ts`，
两侧共用。

## 3. 实施中发现并修复的缺陷

> 全部是**先写完、验收时才发现**的，记录在此以免重犯。

| # | 缺陷 | 现象 | 根因 | 修复 |
|---|------|------|------|------|
| B1 | **首帧相机 X/Z 被镜像** | 换用 FreeViewControls 后初始位姿变成 `[-42, 36, -42]`（应为 `[42,36,42]`） | `createRig` 用 `target - camera.position` 反解球坐标，`theta` 取反 | 改为 `camera.position - target`（`FreeViewControls.tsx::createRig`） |
| B2 | **`V` 键在未限制模式时完全不切** | 点 HUD 按钮能切，按 `V` 无反应 | `KeyV` 分支写成 `if (allowed && ...)`，`allowedModes` 未传时恒为 `undefined` ⇒ 整段跳过 | 缺省补 `FREE_VIEW_MODES` 三态全开 |
| B3 | **动态 FOV 静默失效** | 巡航时 FOV 恒 45° | 文档写缺省增益 10°，代码写 `pr.fovSpeedGain ?? 0` ⇒ 未显式传即关闭 | 提取常量 `DEFAULT_FOV_SPEED_GAIN = 10` 并作为代码缺省（文档与代码对齐） |
| B4 | **键位帮助面板被小地图裁掉前两行** | 帮助面板顶边撞进左上角小地图（z 40 > HUD 32） | 12 条键位单列排布 ≈ 250px，面板从底部向上生长 | 列优先**双列**布局（`--fv-help-rows` 由组件算出 ⌈n/2⌉），面板高度 146px，实测与 minimap 无重叠 |
| B5 | **PerfHud 与新 HUD 抢同一角** | `?debug=1` 下 `tris 414900` 从状态条右侧露出，帮助面板打开时透字 | 两者都是 `left:12; bottom:12` | PerfHud 移到右下角 |

> B1/B2/B3 三者都属于同一类错误：**默认值在文档、props 接口与实现代码三处不一致**，
> 而「不传就用默认值」恰好是最容易被测试跳过的路径。教训：新增 prop 时，
> 缺省值只在**代码常量**里定义一次，文档与接口注释引用它，不复述字面量。

### 4.4 验收环境说明

本机无 GPU，Chrome 走 `--use-angle=swiftshader-webgl` 软件光栅：1000+ draw call 的全城场景
在 1280×720 下约 **0.7 fps**。因此所有交互用例按「≥1 帧/秒」的时间尺度等待（单步 10–20 s），
过渡动画（600 ms 模拟时长，dt 上限 0.1）需约 9 s 真实时间才走完 —— 这是环境限制，
不是实现问题（同一页面空白页 rAF 实测 121 fps，说明不是节流而是软件渲染耗时）。
也因此**逐帧插值连续性**改由 §4.1 的纯逻辑用例（球面/线性插值 + 帧率无关阻尼）保证，
浏览器侧只验证端点与状态机。

## 6. 复现验收的命令片段

```bash
# 纯逻辑
cd ClientWeb && npx esbuild <test>.ts --bundle --platform=node --format=cjs --outfile=/tmp/t.cjs && node /tmp/t.cjs

# 集成（需要 CDP 工具在本机监听）
#   1) POST /api/captcha  → 正则取 <text fill> 中「深色」字符（诱饵是 #cfcfcf/#b9c3d6/#d6c3c9 浅色）
#   2) POST /api/auth/login {account,password,captcha_id,captcha_answer}
#   3) POST /api/games/virtual_city/rooms {name}
#   4) NewChromePage → add_script 写 lsm.auth / lsm.token → navigate /virtual-city/<id>?debug=1
#   5) eval_js 读 window.__freeViewDebug.{mode,position,target,fov,colliding,colliders,bounds,_rig}
```

`?debug=1` 下 `window.__freeViewDebug` 暴露：模式 / 相机位姿 / 聚焦点 / yaw·pitch / fov /
碰撞态 / 过渡态 / 速度档 / 碰撞体数组 / 边界盒 / 内部状态引用（`_rig`，可直接驱动做碰撞复测）。
仅在 `?debug=1` 时挂载，非 debug 零运行时开销（与既有 `__cityRenderInfo` 同一口径）。
